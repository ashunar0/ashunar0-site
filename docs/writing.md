# 記事の書き方

`src/content/posts/` に置く記事を書くときの規約。手順（置き場所・frontmatter）と、文章の規律の両方を置く。
Claude が下書きするときもこれに従う。

## 置き場所と frontmatter

- `src/content/posts/<slug>.md` に置く。**ファイル名がそのまま URL になる**
  - slug は英小文字とハイフン。日本語にすると URL がパーセントエンコードされて共有時に読めない
  - 拡張子は `.md`。`.mdx` だと `<https://...>` の autolink が JSX と解釈されてビルドが落ちる
  - 公開後に slug を変えない。X が掴んだカードは剥がせないので、変えると壊れたリンクが残る
- 画像は `src/content/posts/media/` に置き、`![alt](./media/xxx.png "キャプション")` で参照する。title を付けるとキャプションになる
- **`draft: true` を必ず付ける**。公開判断は本人がする。`false` にするのは明示的に指示されたときだけ

```yaml
---
title: 日本語のタイトル
description: 何が書いてあるかを2〜4文で示す
pubDate: YYYY-MM-DD
tags: [記事ごとに考える]
draft: true
---
```

- `title` は OG 画像の文字に、`description` は X や Slack のカードの説明文にもなる
- `description` はシンプルでよい。基本は内容を具体的に列挙する。ただし「調べてみた」「試してみた」系では列挙しない（結果がオチなので、列挙するとネタバレになる）。題材だけ示して結論は書かない
- `tags` は毎回内容から考える。既存記事に同じ概念のタグがあれば表記を揃える（`設計` と `アーキテクチャ` を混ぜない）。既存のタグは `grep -h '^tags:' src/content/posts/*.md` で見られる
- `pubDate` は並び順のノブとして使っている。同じ日付が 2 本あると並びが不定になるので、そのときは 1 日ずらす
- `updatedDate` は任意

## 書き始める前に

- **既存記事を `pubDate` の新しい順に数本読む**。後の記事ほど文体が磨かれている。ファイル名順で拾わない。古い記事と書き方が食い違ったら新しい方に従う

  ```bash
  grep -H '^pubDate:' src/content/posts/*.md | sort -t: -k3 -r | head -5
  ```

- **ライト記事か通常記事かを先に決める**
  - ライト：2,000〜3,500 字。言いたいことは 1 つで、結論を冒頭に置く。前置きは 1〜2 文、見出しは 3〜4 個まで。3,500 字を超えそうなら話が 2 つ混ざっている
  - 通常：5,000〜8,000 字。冒頭で結論と「何が分かるか」を出す
- **扱う範囲を一文で書く**。書けなければ書き始めない。テーマ（傘）ではなく具体的な現象にする。ぼやけるのは、見えていないものを抽象語でまとめたとき
  - ✗「フレームワークはどこで嘘をつくか」
  - ○「Vue の `ref` は置かれた場所で `.value` の要否が変わる」
  - 話したいことがはっきりしていて、本文がその中身を見せるなら、抽象語の一文でよい（○「Hono が保証するのは API を作れるところまで。hono-kit はそこに、正しく、上手に作るための決まりを足す」）
- 実装レポートと概念の説明を同じ記事に混ぜない
- 「主張を書かない」と本人が決めた記事では、良し悪しの評価・推奨・裁定を書かず、対立する立場は並べて終える。ただしこれはその記事だけの方針で、事実から導ける帰結や教訓はふだん通り書いてよい

## 進め方

- **一節ずつ書く**。骨組みだけファイルに作る → 1 節書く → 意図を説明して反応をもらう → 次の節。本人は各節で判断を返すので、まとめて書くと全部やり直しになる
- 「かけるところから」「ざっくりで」はまとめ書きの許可ではない。「通しで書いて」と明示されたときだけまとめて書く
- 叩き台でも本気で書く
- 修正は該当箇所だけ部分置換する。ファイルを丸ごと書き直さない。本人が直接ファイルを編集していることがあるので、手を入れる前に必ず読み直し、本人の編集を上書きしない
- タイトル・description・見出しは、頼まれたときだけ触る。気になったら口頭で指摘する。公開して X に貼ったあとは戻せない

## タイトル

- その技術や事例が**一言で何を実現するか**で決める。何を作ったか（題材）でも、手段の列挙でもない。未経験の読者にも意味が取れる語で言い切る
  - 例：「Durable Objects でリアルタイムな状態共有を実現する」
- 手段は description に回す
- 硬くしない。口語でよい（「〜なの？」など）。かっこつけない
- 「◯◯に学ぶ、△△の□□」型はすでに使っているので既定にしない。使うなら対象（BaaS 等）を必ず入れる
  - 例：「tl;dv のインシデントに学ぶ、BaaS の「見えない脆弱性」を生む危険性」
- 案を並べる前に「何を実現するか」を確定させ、1 つに絞って推す

## 文体

### 全記事共通

- **硬くしない**。かっこつけず、会話で分かった流れをそのまま出す温度で書く。タイトル・見出し・構成も同じ
- 長さも盛らない。迷ったらライト記事の長さにする

### 技術記事

- 本文は です・ます体。見出しは常体でよい。見出しは `##` / `###`
- **Claude が書く地の文は例外なく です・ます で終える**。特に次の 3 つを潰す
  - 常体の言い切り（「弾かれる。」「場所が無い。」）
  - 体言止め（「そのまま呼べばただの関数。」）
  - 常体の自問（「なぜそんな作りになっているのか。」→「〜のでしょうか。」）
- 書き終えたら、丁寧形で終わらない文を機械的に洗い出す。`grep` の語尾パターンでは取りこぼすので、文末が `ます / ました / ません / です / でした / ですね / ますね / ましょう / でしょう / ください` のどれでもない文を python で拾う。見出し・表・箇条書き・コードは除く
- ただし**本人が書いた崩した口語は意図的**なので直さない。語尾の揺れ・呼びかけ・疑問形が混ざっていても、文体の統一を理由に修正を提案しない。誤字・事実誤り・表記ゆれ（英数字前後のスペース等）は直してよい

### イベントレポート・参加記

- 技術記事の規律の例外。ツイートくらいの口語で、楽しかったことを前に出す。です・ますは軸として残しつつ、「〜しゃべってきました！」「〜かな？」「（笑）」、「！」の重ねを使ってよい
- 本人の言い回しはそのまま残す
- 褒められた話などの自分語りはさらっと書いて、経緯を細かく書かない
- 1 節ずつ質問して、答えから書くと進めやすい

## 書かないこと

- **読者に取り入る導入**。「よくある記事は〜だが実は」「〜で悩んでいませんか」のような、気を引くために作った物語の型。冒頭はゴールだけでよい。書いた動機や経緯をそのまま書くのは問題ない（`## はじめに` も可）
- 記事自身の売り込み（「丁寧に説明しています」）、誰にでも当てはまる対象読者（「つまずきたくない方」）
- **節の終わりの引っ張り**。疑問文で節を終える、次節の予告、結論を伏せた前振り（「ここで問題が起きます」だけ書く）。問いを立てたらその場で答え、結論を先に置いてから展開する。節の最後の一文が橋渡ししか言っていなければ消す
- **当たり前のことを否定の形で書く**こと。読者が持っていない誤解を立てて打ち消しても情報がない。見出しが問うことだけ書く
- 読者の判断に使えない仕組みの解説、設定項目を 1 つずつ解説する表。判断が変わる説明（なぜ必要か、選ばないと後で困る）は書く
- 見れば分かるものの確認手順（GUI アプリの `--version`、Web 登録後のログイン確認）。叩かないと分からない CLI は確認する
- 推測でしか書けない Q&A やつまずき集、捨てる前提のファイルを作らせる練習手順
- 自分の環境・普段のスタックの話（明示的に頼まれた場合を除く）。記事で説明していない関心事を連想で持ち込まない
- 推測の断定。他人の意図は「〜したんだと思います」と書く

## 避ける言い回し

- **「効く」「効いてくる」**、同型の「刺さる」「活きる」「肝になる」。何が起きるかを具体で書く（「後で効いてくる」→「次に似たものを書くときに使えるようになる」）
- **「わけです」**。ほぼ全部削れる
- **検証していない比喩**。書いたら事実として成立するか確かめる。機構を正確に指さないなら、既存の用語か本人の言葉に置き換え、語彙が決まったら旧語彙を `grep` で一掃する
- 直前の文を比喩で言い直すだけの一文
- 「A ではなく B」の対比。B だけ言えば済む
- 溜めてから言う（「もう一段おかしなところがあります」「実は」「先に〜しておきます」）。「最初は〜と思ったが、読んでみると〜だった」のような、思い込みを立ててから種明かしする流れも同じ。言いたいことから言い切る
- 言ったことの念押し（「三つです」の直後に「四つ目はありません」）
- 冒頭で節の構成を予告する定型文（「この記事では、その理由を 3 つの方向から考えてみます。A、B、そして C です。」）。見出しを見れば分かるので書かない
- 箇条書きの頭に `**語。**` を置く型。見出し（`###`）にする
- 分解した項目を `a.` `①` で振って本文で記号参照すること。本文でそのまま使える名前を付ける

## 古くならない書き方

- 対話式プロンプトは引数で回避する（`npm create vite@latest my-app -- --template react`）
- Web UI の画面遷移を細かく書かない。「表示が違っても、これができれば完了」と逃げ道を作る
- バージョンは必要なときだけ固定し、確認先の URL を添える

## 本文の記法

- 段落に URL を単独で置くとリンクカードになる。流れを切りたくない場所では `[テキスト](url)` にする
- コードブロックの AA 図は揃えに関わる部分を全部 ASCII にし、日本語は行末にだけ置く。罫線は `+---+` と `|`。本番の等幅フォントで日本語が 2 倍幅にならず崩れる
- 参考リンクは本文末の `## 参考` に置き、URL は貼る前に到達確認する

## 公開

- main への push が本番デプロイになる（GitHub Actions）。`draft: true` のままなら push しても本番には出ない
- `pubDate` が未来の記事は、その日の定時ビルド（毎朝 09:05 JST）まで本番に出ない（予約公開）
- 公開したら本番 URL が 200 を返すか確かめてから共有する

  ```bash
  curl -s -o /dev/null -w "%{http_code}\n" "https://ashunar0.dev/posts/<slug>/?cb=$RANDOM"
  ```
