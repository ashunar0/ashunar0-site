## はじめに

最近 Twitter では、ORM 不要論や生 SQL 回帰論が話題に上がっています。「ORM は要らない」「生 SQL でいい」「いやクエリビルダくらいは欲しい」といった意見が見受けられますが、自分には正直よくわかりませんでした。

というのも、僕は「SQLを書くの面倒」「軽量」「なんとなく読みやすい」というあまりにも短絡的な理由で、Drizzleしか使っていないからです！！

とはいえ、こうも話題に上がっている以上、何も学ばずにスルーするというのもいささかもったいない気がしたので、ORM が実際に何を引き受けているのかを分解してみることにしました。この論争の解像度が少しでも上がればいいなと思いながら調べています。

## 「ORM」が指すものの幅

分解の前に、用語の話をします。

ORM は Object-Relational Mapping の略で、名前の通りならオブジェクトとリレーショナルデータベースの間を橋渡しするものです。ただ、この名前で呼ばれているライブラリの実物は、かなり違う姿をしています。

たとえば、Rails の ActiveRecord では、テーブルがクラスになり、行がそのインスタンスになります。

```ruby
user = User.find(1)
user.name = "asahi"
user.save
user.posts.each { |post| puts post.title }
```

`user.posts` と書くだけで関連するレコードが取れます。SQL は表に出てきません。

Prisma は、クラスではなくクライアント経由でデータを取ります。

```ts
const user = await prisma.user.findUnique({
  where: { id: 1 },
  include: { posts: true },
});
```

`include: { posts: true }` が JOIN になるのか別クエリになるのかは、書いた側からは決められません。ここも SQL は表に出てきません。

Drizzle になると、また様相が変わります。

```ts
const rows = await db
  .select()
  .from(users)
  .innerJoin(posts, eq(posts.userId, users.id))
  .where(eq(users.id, 1));
```

`select` `from` `innerJoin` `where` と並んでいて、SQL の構造がそのまま残っています。返ってくるのもオブジェクトのグラフではなく、JOIN した結果の行の集まりです。（個人的にはこれがいちばんしっくり来てます。）

この3つが同じ「ORM」という語で呼ばれています。ActiveRecord を思い浮かべている人と Drizzle を思い浮かべている人が「ORM は要る / 要らない」を議論しても、話が合わないのは自然だと思います。

## ORM が引き受けている責務

そこで、名前で呼ぶのをやめて、中で何をやっているかを棚卸してみましょう。ORM と呼ばれるライブラリが引き受けている仕事は、だいたい次の7つに分かれます。

| | 責務 | 内容 |
| --- | --- | --- |
| a | クエリの組み立て | SQL 文字列を直接書かずにクエリを作る。多くは型が付く |
| b | 行とオブジェクトの変換 | 取得した行をアプリ側のオブジェクトに詰め替え、書き戻す |
| c | 関連の解決 | 関連レコードを属性のように辿る。まとめて取るか都度取るかを選べる |
| d | スキーマの単一情報源 | テーブル定義をコードの一箇所に置き、そこから型などを導く |
| e | マイグレーション | スキーマの変更を差分として記録し、順に適用する |
| f | インジェクション対策 | 値をプレースホルダとして扱い、SQL 文字列に埋め込ませない |
| g | トランザクション管理 | 一連の操作を一つの単位としてまとめ、まとめて確定または取り消す |

それぞれ簡単に見ていきます。

### a. クエリの組み立て

`db.select().from(users).where(...)` のように、メソッドを繋いでクエリを作る部分です。ここに型が付いていると、存在しないカラム名を書いた時点でエラーになります。

ライブラリによって SQL からの距離が違います。Drizzle や Kysely は SQL の構文にかなり寄せていて、Prisma の `findMany` は離れています。

### b. 行とオブジェクトの変換

データベースから返ってくるのは行の集まりで、アプリケーションの中で扱いたいのはオブジェクトです。この間を埋めるのがこの責務です。

ActiveRecord の `user.name = "asahi"; user.save` は、オブジェクトへの代入を UPDATE 文に変換しています。逆方向も同じで、取得した行の各カラムをオブジェクトの属性に詰めます。

### c. 関連の解決

`user.posts` のように、関連するレコードを属性として辿れるようにする部分です。

取り方には2通りあります。ユーザーを取る時点で投稿もまとめて取っておく方法と、`user.posts` に触れた瞬間に改めてクエリを投げる方法です。前者を eager loading、後者を lazy loading と呼びます。

### d. スキーマの単一情報源

テーブルの定義をコードの一箇所に置いて、そこを正とする部分です。Prisma の `schema.prisma` や、Drizzle の `schema.ts` がこれにあたります。

```ts
export const users = pgTable("users", {
  id: serial("id").primaryKey(),
  name: text("name").notNull(),
});
```

ここが決まっていると、アプリ側の型もマイグレーションもここから導けます。定義がコードとデータベースの両方にあって食い違う、という状態を避けるための責務です。

### e. マイグレーション

スキーマの変更を差分として記録して、順番に適用する部分です。`drizzle-kit generate` のように、d のスキーマ定義から差分を自動生成するものもあります。

d と e はよく一緒に語られますが、別の仕事です。d は「今のスキーマはこれ」を持つことで、e は「どう変わってきたか」を持って適用することです。

### f. インジェクション対策

値を SQL 文字列に埋め込まず、プレースホルダとして渡す部分です。

```ts
// 値が文字列に混ざる
`SELECT * FROM users WHERE name = '${name}'`

// 値はプレースホルダ経由で渡る
db.select().from(users).where(eq(users.name, name))
```

クエリを組み立てる API を通す限り、後者の形にしかならないので、埋め込みが構造的に起きなくなります。

### g. トランザクション管理

複数の操作をまとめて確定または取り消す部分です。

歴史的には、ORM 側でオブジェクトの変更を溜めておいて、最後にまとめて書き戻すという設計がありました。Hibernate のセッションがその形です。ただ最近のライブラリでは、`db.transaction()` でデータベース側のトランザクションを囲むだけ、という薄い形が多くなっています。

## 責務は別々に取り外せる

7つに分けてみて分かったのは、これらが必ずしもひとまとめで提供されるものではない、ということです。それぞれを単体で引き受けるツールが、実際に存在します。

### マイグレーションだけを引き受けるもの

[dbmate](https://github.com/amacneil/dbmate) は、マイグレーション（e）だけを担当する CLI です。マイグレーションは素の SQL ファイルとして書き、up と down を持ちます。特定の言語やフレームワークに紐づいていないので、Go でも Node.js でも Ruby でも同じように使えます。

[Atlas](https://atlasgo.io/) はもう少し踏み込んでいて、スキーマを宣言的に書くと、今のデータベースとの差分を計算してマイグレーションを組み立てます。d と e の両方を引き受けている形です。こちらも ORM に紐づいておらず、SQL / HCL / 各言語の定義から入れます。

どちらも、アプリケーション側で何を使っているかとは独立して導入できます。

### クエリの組み立てだけを引き受けるもの

[Kysely](https://kysely.dev/) は TypeScript のクエリビルダです。SQL の構文に沿ってメソッドを繋いでクエリを作り、結果に型が付きます。a と f を引き受けている一方で、b と c にあたる機能は持ちません。行はオブジェクトのグラフにならず、そのまま返ってきます。

なお Kysely にも `Migrator` があるので、e も持っています。ただし d は持っていません。テーブルの型は `Database` インターフェースとして別に用意する必要があり、マイグレーションもそこから自動生成されるわけではなく手で書きます。

### 生 SQL のまま型だけを付けるもの

[SafeQL](https://safeql.dev/) は ESLint プラグインです。コード中に書かれた生の SQL 文字列を、実際の PostgreSQL のスキーマと突き合わせて検証し、結果の型を推論します。

```ts
const users = await sql`SELECT idd FROM users`;
//                             ^ カラム名の誤りがエディタ上で分かる
```

クエリは SQL のまま書きます。クエリビルダを通さずに、a の型安全だけを取ってくる形です。

### 分解してみて見えること

こうして並べてみると、「ORM を使う / 使わない」という選び方が、実際にはもう少し細かい選択の集まりだったことが見えてきました。たとえば ORM を外しても、d と e を Atlas に、a と f を Kysely に任せるという組み合わせが成り立ちます。この場合、手放しているのは b と c だけです。

議論の中で「Kysely + Atlas + Kanel」「生 SQL + SafeQL + dbmate」といった具体的な構成名が挙がることがありますが、これは7つの責務を別々のツールに割り当てた結果を書いている、ということになります。

## 意見がどの責務を指しているか

ここまでの分解を持って、最初の議論に戻ってみます。流れてきた意見を責務に対応づけると、次のようになります。

| 意見の要旨 | 指している責務 |
| --- | --- |
| オブジェクトと行の変換は30年うまくいっていない | b |
| ORM を使えばインジェクションを防げる | f |
| テーブルをクラス、行をオブジェクトとして扱える | b |
| 関連を属性として辿れて、まとめて取るか都度取るかも選べる | c |
| モデル定義を正としてマイグレーションと繋げられる | d, e |
| 生 SQL でいいと言うならマイグレーション管理の代案も出してほしい | d, e |
| クエリビルダくらいの制約は欲しいので Kysely | a, f |
| 生 SQL のままでいいので SafeQL を使えばいい | a |
| ORM は初心者のためのガードレールだったが、AI が書くなら要らない | 全体 |

同じ「ORM は要る / 要らない」という形の発言でも、指している責務が違います。b について「要らない」と言っている人と、d と e について「要る」と言っている人は、そもそも重なっていません。

また、どの意見も7つ全部を対象にしているわけではないことも分かります。「ORM 不要」と書かれているものの多くは b と c を指していて、d や e に反対しているわけではありません。

## なぜ変換と関連の話ばかりが議論されるのか

7つのうち、批判が集中しているのは b と c です。ここだけ扱いが違うのはなぜなのかが気になったので、もう少し調べました。

### オブジェクトと関係モデルは構造から違う

オブジェクトの世界とリレーショナルデータベースの世界がうまく噛み合わない、という話には「インピーダンスミスマッチ」という呼び名が付いています。よく引かれるのは、2006年に公開された Ted Neward の [The Vietnam of Computer Science](https://blogs.newardassociates.com/blog/2006/the-vietnam-of-computer-science.html) というエッセイです。もとは2004年の講演だったものです。

このエッセイでは、両者の食い違いがいくつか挙げられています。読んで分かりやすかったものを4つ引きます。

#### 同一性の扱いが違う

オブジェクトは、中身が同じでも別の場所にあれば別物です。一方リレーショナルモデルでは、状態が同じ行が2つあること自体がデータの壊れた状態として扱われます。

#### 継承の置き場所がない

オブジェクトには継承がありますが、テーブルにはその構造がありません。親クラスと子クラスをどうテーブルに落とすかは、テーブルを分けて JOIN するか、一枚にまとめて使わない列を許すか、といった選択になります。どれを選んでも何かを諦めます。

#### 関連の向きが逆

オブジェクト側では、参照する側が参照される側を持ちます。データベース側では、外部キーを持っているのは参照される側のほうです。向きが反対なので、双方向に辿れるようにしようとすると、どちらかを作り出す必要があります。

#### 取得の粒度が違う

SQL は必要な列だけを取ってくることができますが、オブジェクトは属性を一部だけ持った状態になれません。そのため、全部読むか、空のままにしておくか、後から必要になった時点で読みに行くか、を決めることになります。

これらは実装の出来不出来ではなく、モデルの構造そのものから来ています。うまく実装すればなくなる、という種類のものではありません。「30年やって撤退を繰り返している」と言われるのは、この辺りを指しているようです。

### 後から読みに行くと N+1 になる

上の「取得の粒度が違う」から派生するのが N+1 です。関連を後から読みに行く（lazy loading）と、こうなります。

```ruby
users = User.limit(10)
users.each do |user|
  puts user.posts.count
end
```

最初にユーザーを取る SELECT が1本、そのあと `user.posts` に触れるたびに SELECT が1本ずつ、合計11本のクエリが飛びます。ユーザーが100人なら101本です。

書いている側のコードには、クエリが飛ぶことを示す記述がありません。`user.posts` は属性を読んでいるように見えます。c の「関連を属性のように辿れる」という便利さと、この挙動は同じ仕組みから出ています。

一方、a しか持たないクエリビルダでは、この形は起こりません。`user.posts` に相当する記述がなく、JOIN するなら JOIN と書くからです。b と c を持つかどうかで話が変わるのは、こういう部分です。

## AI が書くなら、という論点

今回の議論には、これまでになかった軸も混ざっていました。コードを書くのが人間とは限らなくなった、という前提の話です。

これは7つの責務のどれか、という分け方には乗りません。「どの責務が要るか」ではなく「誰が書くか」の話だからです。見かけた立場を3つ並べておきます。

ひとつは、ORM は品質を揃えるためのガードレールだった、という見方です。SQL に慣れていない人が書いても一定の水準になるように ORM を採用していたのであれば、AI が書くならその理由は薄くなります。

もうひとつは、AI が書くからこそ制約が要る、という見方です。生成されたクエリがそのまま本番に入る可能性を考えると、書ける形をある程度絞っておきたい。クエリビルダくらいの枠は残したい、という立場です。

3つめは、コンテキストの観点です。抽象化して済むものを毎回 AI に生成させるのは無駄で、抽象化できるなら抽象化しておけばいい、という見方になります。

また、d と e をこの文脈で見直す意見もありました。エージェントにデータベースを触らせる場合、今のスキーマがどこに書いてあるのか、変更をどう適用して戻すのかが決まっていないと成立しません。逆にスキーマが一箇所に揃っていれば、型もマイグレーションもそこから導けます。

## おわりに

ORM が引き受けている仕事を7つに分けて、それぞれを単体で担うツールがあることと、議論の中の意見がどこを指しているかを並べました。

分かったのは、「ORM は要るか」という問いの形だと、聞かれた人がどの責務を思い浮かべるかで答えが変わってしまう、ということです。ActiveRecord を思い浮かべた人と Kysely を思い浮かべた人では、同じ質問に別のことを答えます。

責務ごとに見れば、それぞれ別の話でした。b と c には構造から来る難しさがあり、d と e は ORM から切り離しても持てて、a と f はクエリビルダの範囲で足ります。どれを何に任せるかは組み合わせの問題で、まとめて決めなければならないものではありませんでした。

良し悪しについては、今の僕にはまだ判断がつきません。ただ、流れてくる意見がどこを指しているのかは、前より読めるようになりました。定期的に発生する ORM 不要論、次に話題になるときには、自分の意見が持てるようになっているといいな。
