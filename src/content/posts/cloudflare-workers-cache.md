## はじめに

先月、CloudflareにWorkers Cacheという新機能が登場して、ついにWorkerの手前にキャッシュを置けるようになりました！キャッシュにヒットしたリクエストでは、**Workerが1行も実行されません**。

しかも設定は`wrangler`に1行足すだけです。あとは`Cache-Control`ヘッダーで制御します。この記事では、設定・キャッシュキー・tiered cache・purge・料金・現時点の制約の順に見ていきます。

## なぜこれが待望だったのか

Cloudflareのリクエスト処理は、これまでWorkerが先でキャッシュが後ろでした。リクエストが届くとまずWorkerが起動して、そのコードの中から`caches.default`を叩いたり`fetch()`でオリジンに取りに行ったりします。

```
リクエスト → Worker起動 → Cache API / オリジン
```

もう図の時点で分かると思うんですが、キャッシュにヒットしても**Workerは毎回起動します**。ヒットしたかどうかを判定するのがWorkerのコード自身なので、構造上そうならざるを得ません。

これがSSRだと結構つらいです。たとえば1時間まったく更新のないトップページに10万件のリクエスト来たら、Workerは10万回起動しちゃいます。

`caches.default`で自前キャッシュを持てばいいじゃん、と思うところですが、そうもいきません。「キャッシュを引いて返す」という処理自体がWorkerの中で走るので、結局CPU時間は請求されます。**Workerを動かさずに済ませる手段が、そもそも無かった**んですよね。

そしてCache APIには、もうひとつ弱点がありました。同時リクエストをまとめてくれないんです。

キャッシュが空のURLにアクセスが集中したところを想像してみてください。全部が揃ってミスします。全部がWorkerを起動します。そして全部が裏のDBやAPIを叩きに行きます。いわゆるcache stampedeというやつで、防ぐには自分でロックを組むしかありませんでした。

ゾーン側のCache RulesやPage Rulesは、というと、こちらはこちらでWorker上で完結するアプリケーションを想定した作りではありませんでした。ダッシュボードのルールエンジンとコード側のキャッシュ制御が別々の場所にある、という状態です。

## 何が変わったのか

Workers Cacheでは、この順番をまるごと入れ替えます。

```
リクエスト → キャッシュ →（ヒットならここで終わり。Workerは動かない）
                └ ミス → Worker起動 → レスポンスを保存
```

さっきの10万リクエストが、Worker起動1回で済みます。残り99,999回のCPU課金はゼロです。SSRやSSGをWorkerでやっている人にとっては、そのまま請求書が軽くなります。

そして、request collapsingも入りました。キャッシュが空のURLに同時アクセスが殺到しても、Cloudflareが待ち合わせて**Workerを1回だけ実行し、その結果を待っている全員に配ります**。さっきのcache stampedeが、何も書かずに消えます。自前でロックを組んだことがある人ほど効くと思います。ドキュメントでもここをCache APIとの最大の違いとして挙げていました。

そしてもうひとつ。このキャッシュは**ゾーンではなくWorkerのentrypointに属します**。Cache Rulesもcache levelの設定も拡張子リストもPage Rulesも、Workers Cacheには一切適用されません。つまりキャッシュの挙動を知りたければ、Workerのコードと`wrangler`の設定だけ読めば済みます。ダッシュボードを開かなくていいの、地味にめちゃくちゃありがたいです。

## 設定は wrangler の1行だけ！

有効化はこれだけです。

```jsonc
// wrangler.jsonc
{
  "cache": { "enabled": true }
}
```

以上です！ゾーンの用意も、ルールエンジンの設定も、別プロダクトへのログインも要りません。

entrypointごとに切り替えたい場合は`exports`で上書きします。公開ページはキャッシュしたいけど管理画面はしたくない、みたいなケースですね。

```jsonc
{
  "cache": { "enabled": true },
  "exports": {
    "Admin": { "cache": { "enabled": false } }
  }
}
```

環境ごとの出し分けもできるので、本番だけONにして開発中は素通し、という運用もそのまま書けます。

なお、キャッシュはデフォルトでWorkerのバージョンごとに分かれています。デプロイすると空の状態から始まる、ということです。バージョンを跨いで使い回したい場合は`cross_version_cache`を有効にします。

### あとはCache-Controlで制御する

Workerの側でやることは、レスポンスにヘッダーを付けるだけです。独自のAPIを覚える必要がないのがいいところ。

```js
return new Response(html, {
  headers: {
    "Cache-Control": "public, max-age=60, stale-while-revalidate=300",
  },
});
```

使うディレクティブは見慣れたものばかりです。

| ディレクティブ | 意味 |
|---|---|
| `max-age` | 何秒間フレッシュとして扱うか |
| `stale-while-revalidate` | 期限切れでも古いものを即座に返し、裏でWorkerを回して更新する |
| `stale-if-error` | Workerが失敗したときに古いものを返す |
| `no-store` | キャッシュしない |

特に`stale-while-revalidate`が強力で、この窓の中にいるリクエストは待たされません。古い方を即座に受け取って、更新はバックグラウンドで走ります。このとき`Cf-Cache-Status: UPDATING`が返るので、ヘッダーを見れば今どの状態なのか分かります。

ヘッダーが競合したときの優先順位はこうなっています。CDN向けだけ挙動を変えたい場合に使うやつです。

1. `cloudflare-cdn-cache-control`
2. `cdn-cache-control`
3. `Cache-Control`

### 何も付けなかったら

`Cache-Control`を書き忘れても素通しにはならず、ステータスコードに応じたデフォルトTTLが効きます。ここは知らないとハマるところかもしれません。

| ステータス | TTL |
|---|---|
| 200 / 203 / 204 | 2時間 |
| 300 / 301 | 20分 |
| 404 / 410 | 3分 |
| 405 / 414 / 501 | 1分 |

逆に、どうやってもキャッシュされないものもあります。520〜526番台のレスポンスと、`Vary: *`が付いたレスポンスです。`Range`リクエストは、キャッシュ済みの完全なレスポンスから切り出して返されます。

## キャッシュキーに何が入るか

キャッシュはキーが同じなら同じレスポンスを返します。なので知っておきたいのは、**どこまでが「同じリクエスト」として扱われるのか**です。

ここの認識がずれると、2方向に事故ります。本来違うものが同じキーに落ちれば、他人宛のレスポンスが返ります。逆に本来同じものが別キーに散れば、いつまでもキャッシュに当たりません。

キーの中身を見てみましょう。

- **entrypoint** — リクエストを受けた名前付きexport
- **パスとクエリ文字列**
- **Workerのバージョン**（デフォルト。前述の`cross_version_cache`で外せます）
- **`ctx.props`** — service bindingやRPC経由で呼ばれたときに渡される値

このほか、`x-forwarded-host`や`x-http-method-override`のような、フレームワークがリクエストの書き換えとして解釈しうるヘッダーも含まれます。cache poisoningを防ぐためですね。

### ホスト名は入りません

さっき挙げたキーの構成要素に、**ホストは入っていません。**

普通のHTTPキャッシュはURL全体、つまりホスト込みでキーを作ります。Cloudflareのこれまでのキャッシュもゾーン単位でした。なので「キャッシュはドメインごとに分かれている」というのが多くの人の直感だと思うのですが、Workers Cacheはその限りではありません。

`/api/users/42`へのリクエストは、`api.example.com`から来ようが、service binding経由だろうが、`workers.dev`のURLだろうが、**全部同じキャッシュエントリに当たります**。

これが刺さるのは、1つのWorkerを複数のドメインに割り当てて、`Host`ヘッダーを見て出し分けている場合です。ホワイトラベルのSaaSではよくある構成ですね。

```
a-corp.example.com/  ─┐
                      ├─→ 同じキャッシュエントリ
b-corp.example.com/  ─┘
```

B社のトップページを開いたらA社の中身が出ます。しかもキャッシュが温まってから起きるので、ローカルでもステージングでも再現しません。回避するなら、`Host`を明示的にキーへ持ち込む必要があります。手前にWorkerを置いて、テナントを`ctx.props`で渡すか、`cf.cacheKey`にホストを含めるかです。

```js
return ctx.exports.Backend.fetch(request, {
  cf: { cacheKey: url.host + url.pathname + url.search },
});
```

逆に言うと、ホストが入らないおかげでキャッシュ効率は最大化されます。同じWorkerの同じパスなら、入口がどこでも1つのエントリを共有できるからです。設計としてはそちらを取った、ということですね。

### クエリの順番も区別されます

`?a=1&b=2`と`?b=2&a=1`は別のキーです。内容が同じでも別エントリになります。

これが地味に効いてくるのがトラッキングパラメータで、`?utm_source=twitter`が付いただけでキャッシュミスになります。SNSから流入するページだと、リンクの出どころごとにキャッシュが分裂します。

これを避けたい場合は、手前のWorkerから`cf.cacheKey`でキーを差し替えられます。

```js
export default {
  async fetch(request, env, ctx) {
    const url = new URL(request.url);
    url.searchParams.delete("utm_source");
    return ctx.exports.Backend.fetch(request, {
      cf: { cacheKey: url.pathname + url.search },
    });
  },
};
```

差し替えられるのはパスとクエリの部分だけです。entrypointと`ctx.props`は自動的にキーに残るので、これで他人のキャッシュを踏むことはありません。

### ctx.propsでテナントが混ざらない

キャッシュで一番怖いのは、AさんのページがBさんに返ることです。

Workers Cacheでは`ctx.props`がキーの一部なので、**違う`ctx.props`で呼ばれた2つのリクエストは別エントリになります**。ドキュメントの表現でも「一方の呼び出し元が他方のキャッシュされたレスポンスを受け取ることは決してない」と言い切っています。ユーザーIDやテナントIDをpropsで渡しておけば、分離はプラットフォーム側が保証してくれる形です。

### Varyで同じURLに複数の姿を持たせる

`Vary`レスポンスヘッダーを返すと、そこに挙げたリクエストヘッダーの値ごとに別々のvariantが保存されます。

たとえば`Accept`を見てWebPとJPEGを出し分けているWorkerなら、`Vary: Accept`を付けるだけで両方がキャッシュされます。1つのURLに2つの姿を持たせられます。

ただしvariantは**ヘッダー値の完全一致**で分かれます。`Accept-Encoding: gzip, br`と`Accept-Encoding: br, gzip`は、意味が同じでも別のvariantとして保存されてしまいます。`User-Agent`のように値の種類が多いヘッダーで`Vary`すると、キャッシュが際限なく分裂するので注意が必要です。

## tiered cacheがデフォルトで効く

Cloudflareのデータセンターは世界に300以上あります。ここで素朴に考えると、キャッシュがデータセンターごとに独立していたら、**都市の数だけWorkerが起動する**ことになりますよね。たとえば、東京で1回、大阪で1回、ロンドンで1回、みたいな。

Workers Cacheは、これを2段構えで解いています。

- **下位ティア** — ユーザーにいちばん近いデータセンターのキャッシュ
- **上位ティア** — 下位ティアがミスしたときに問い合わせにいく、少数のデータセンター

下位ティアが外したら、いきなりWorkerを起動するのではなく、まず上位ティアに聞きにいきます。そこにあれば、Workerは動きません。

つまり**世界のどこかで最初の1リクエストが上位ティアを埋めたら、あとはどのデータセンターからのアクセスでもWorkerなしで返せます**。デプロイ直後にアクセスが世界中から来ても、Workerが起動するのは実質1回です。

これが嬉しいのは、キャッシュが冷たい時間が短くなることです。従来のようにデータセンターごとに独立していると、アクセスの少ない地域はいつまでもキャッシュが温まらず、その地域のユーザーだけずっと遅い、ということが起きます。上位ティアがあると、誰かが1回踏んだ恩恵を全員が受けられます。

そしてこれ、**設定は何も要りません**。デフォルトで有効ですし、別料金もかかりません。トポロジを選んだり、上位ティアの場所を指定したりする必要もないです。さすが天下のCloudflare。すばらしい。

## purgeはコードから叩ける

TTLで期限切れを待つだけだと、記事を更新したのに5分間古いままです。それは困るので、明示的に消せる必要があります。

Workers Cacheのpurgeは、Workerのコードから直接呼べます。

```js
await ctx.cache.purge({ tags: ["post-123"] });
```

このためには、レスポンスを返すときに`Cache-Tag`を付けておきます。

```js
return new Response(html, {
  headers: {
    "Cache-Control": "public, max-age=3600",
    "Cache-Tag": "post-123,author-42,blog-posts",
  },
});
```

こうしておくことで、記事を1本更新したときは`post-123`で消せますし、著者名を変えたときは`author-42`で**その人の記事だけまとめて**消せます。ブログ全体のレイアウトを変えたなら`blog-posts`です。1つのレスポンスに複数の切り口を持たせておけるのが効いてきます。

タグではなく、パスのprefixで指定することもできます。両方を1回で渡すのもアリで、その場合は**どちらかに当てはまるもの**が消えます。ANDではなくORですね。

```js
await ctx.cache.purge({
  tags: ["blog-posts"],
  pathPrefixes: ["/blog/"],
});
```

全部消すときは`purgeEverything`です。これだけは他と併用できません。

```js
await ctx.cache.purge({ purgeEverything: true });
```

purgeの効果は**呼び出したentrypointの中だけ**に閉じています。同じアカウントの別のWorkerのキャッシュを巻き込むことはないので、消す範囲を心配しなくて済みます。

タグの制限も一応載せておきます。

| 項目 | 制限 |
|---|---|
| 1レスポンスあたりのタグ数 | 1000個まで |
| タグ1つの長さ | 1024文字まで |
| 使える文字 | 印字可能なASCII |
| 大文字小文字 | 区別しない |

なお、purgeはキャッシュを**消します**。消えたあとの最初のリクエストはミスになるので、そのユーザーはWorkerの実行を待つことになります。ここについては、消す代わりにstaleとして印を付ける`ctx.cache.invalidate()`が予定されています。これが入ると、更新直後のユーザーも古いものを即座に受け取れて、裏で新しいものに差し替わる形になります。今はまだ使えません。

## 料金は安くなる、とは限らない

まず基本の表です。

| | リクエスト課金 | CPU課金 |
|---|---|---|
| ヒット | かかる | **かからない** |
| ミス / バイパス | かかる | かかる |

ヒットしたリクエストはWorkerを起動しないので、CPU時間を請求されません。専用のSKUもなければ、キャッシュ容量あたりの保管料も取られません。tiered cacheもpurgeも`stale-while-revalidate`も分析画面も、全部この中に含まれています。しかも無料プランを含む全プランで使えます。

ここまでは良い話しかないんですが、ひとつ注意点があります。

### 無料だったリクエストが有料になります

キャッシュを有効にすると、**これまで無料だったリクエストが標準のリクエスト料金で課金されるようになります**。対象は2つです。

- 静的アセットへのリクエスト
- service bindingや`ctx.exports`経由のWorker間呼び出し

理由は単純で、有効化した時点で**これらもWorkerの手前のキャッシュを経由するようになる**からです。キャッシュを引く以上、リクエストとして数えられます。

なので、CPU時間が減る分と、無料だったリクエストが有料になる分の、差し引きで考える必要があります。

- CSSや画像を大量に配っていて、Worker側の処理は軽い → 増える可能性があります
- SSRでCPUを使っていて、アセットはさほど多くない → だいぶ減るはずです
- 内部でWorkerを何段も呼び分けている → 呼び出し回数がそのまま乗ってきます

ONにする前に、自分のトラフィックがどの型なのかを見ておくと安全です。「1行足すだけ」で入れられてしまう手軽さがあるぶん、ここは意識しておきたいところですね。

## 現時点の制約

出たばかりなので、まだ整っていないところもあります。

### fetch()以外はキャッシュを通りません

キャッシュを経由するのは`fetch()`の呼び出しだけです。RPCのメソッドを直接呼ぶ形、たとえば`ctx.exports.Backend.getUser(id)`のような書き方だと、キャッシュは丸ごとスキップされます。

Workerを型付きRPCで繋いでいる構成だと、ここは効いてきます。キャッシュに乗せたい経路だけ`fetch()`で書く、という設計判断が必要になりますね。

また、`Authorization`ヘッダーが付いたリクエストは自動的にバイパスされます。ログインが必要なページをキャッシュしたい場合は、手前にWorkerを置いて認証を済ませ、`Authorization`を外してから`ctx.exports`で内側を呼ぶ形になります。ユーザーの区別は前述の`ctx.props`が引き受けてくれます。

### レスポンスサイズの上限が暫定です

現在は**どのアカウントでも無料プランと同じ512MB**が上限になっています。有料プランでもこの値です。

これは一時的な状態で、ロールアウトが進めばプランごとの標準の上限が適用されるとのことです。大きなファイルを扱う予定があるなら、頭の片隅に置いておくとよさそうです。

### Smart Placementとまだ噛み合っていません

Smart Placementの配置先と、上位ティアのデータセンターは、それぞれ独立に選ばれます。

なので完全にミスしたリクエストは、上位ティアまで行って、そこからさらにSmart Placementの配置先まで行く、という**長距離の往復を2回**踏む可能性があります。ここは今後協調させる予定だそうです。

### invalidate()はまだ来ていません

purgeの節で触れたとおり、消す代わりにstale扱いにする`ctx.cache.invalidate()`は予定されている段階です。これが入るまでは、purge直後の1人はWorkerの実行を待つことになります。

## おわりに

Workerの手前にキャッシュが来た、というだけの話ではあるんですが、これまで構造上どうにもならなかったところが1行の設定で解けるようになったのは大きいと思います。

一方で、ホストがキーに入らない件や、無料だったリクエストが課金対象になる件のように、素直に入れると事故るポイントもあります。特に前者は温まってから初めて表面化するので、複数ドメインを1つのWorkerで捌いている人は先に確認しておくのがよさそうです。
