## はじめに

ここ数日、Twitter のタイムラインで「Jev」なるものをよく見かけるようになりました。どうやら、文章を書かない AI で、今までの LLM とは一線を画す新たな存在らしいです。調べてみると、、、なんかめちゃくちゃ面白そう！！

印象としては、ポケモンの NPC の AI に近いものを感じました。いちいち文章に起こさず、技のコマンドを入力するだけ、みたいな。（もちろんあれは人間がルールを決めているものですが）

なにやら今後大きな影響を与えてきそうな予感がするので、まとめてみることにしました。

## Jev とは何か

Jev は、TypeSafe AI という会社が 2026 年 9 月 15 日に発表した新たな AI モデルです。Claude や GPT、Gemini と同じ階層の名前で、TypeSafe AI が「System One Model」と呼ぶ新しい種類のモデルの第 1 号にあたります。創業者の Diogo Almeida は元 OpenAI の研究者で、言語モデルに指示を守らせ、人と会話できるようにした手法を作った人らしいです（その研究が ChatGPT の土台になったそうな）。

Jev の一番の特徴は、**文章を書かず、あらかじめ型を決めた質問に対して、その型の値だけを返す**ことです。LLM に質問すると答えが文章で返ってきますが、Jev は文章を生成する機能をそもそも持っていません。代わりにたとえば、「このメールは A / B / C のどれ？」と聞いたらその選択肢のどれかだけが返り、「この文は真か？」と聞けば 0 から 1 の数値だけが返ります。

TypeSafe AI は、Jev を LLM の小型版や派生ではなく、LLM とは別の新しい種類のモデルだと位置づけています。公式の FAQ には "Jev is neither small nor an LLM" とあり、その種類の名前が System One Model です。発表記事には次のように書かれています。

> While Jev gives up string generation, it's optimized for structured outputs and *can't* hallucinate.

文章生成を捨てた代わりに、構造化された出力に最適化されていて、幻覚を起こせない、という説明です。「起こさない」ではなく「起こせない」なのは、返す値が型で決まっているからです。選択肢が A / B / C なら、その外の値は構造上出てきません。（ただし、A が正解のときに B を自信満々に選ぶことはあり、「間違えない」という意味ではないのでその点は注意が必要っぽいですね。）

## LLM との違い

LLM と System One Model の違いを、TypeSafe AI の発表記事とドキュメントに書かれている範囲で並べてみます（数値はいずれも TypeSafe AI 自身の測定で、第三者による検証はまだ見つかっていません）。

| 観点 | LLM | Jev |
|---|---|---|
| 出力 | 文章をトークンごとに順番に生成する | 事前に決めた型の値を一度に返す |
| 得意なこと | 会話、文章の作成、コード生成、説明 | 分類、振り分け、採点、真偽の判定 |
| 応答時間 | 3 秒〜329 秒（発表記事の測定値） | 70ms〜500ms |
| 料金 | 入力と出力の両方に課金 | 入力 $0.042 / 100 万トークン、出力は無料 |
| 幻覚 | 起きる | 型の外の値は出ない |

Jev は答えを文章ではなく、「決められた型」の値で返します。そのため答えの長さという概念がなく、応答は 1 秒未満という超爆速で返り、出力トークンへの課金もありません。返す値は型の範囲に収まるので、範囲の外の値が出ることもありません。速くて安い！最高です。

たとえば「このメールは営業メールですか？」と聞くと、LLM なら「はい、これは営業メールです。理由は〜」という長ったらしい文章をつらつらと書いてきますが、Jev は「営業メール / それ以外」のどちらかだけが返ってきます。文章から答えを取り出す処理がいらないので、判定結果をそのままコードに組み込むことも可能です。

Jev はこうした判断の課題では既存の LLM と同程度の性能を保ったまま、2 桁速く、2 桁効率が良いとのことです。

## 質問の型は 3 つだけ

Jev への呼び出しは、判断の材料になる「state」と、型付きの「question」の 2 つで組み立てます。question の型は次の 3 つしかありません。

| 型 | 聞くこと | 返るもの |
|---|---|---|
| Choice | 選択肢の中からどれか | 選んだ選択肢、各選択肢の確率、確信度 |
| Score | 段階の中でどのあたりか | 段階の位置を示す数値、各段階の確率、確信度 |
| Noul | この命題は真か | 真である確率（0〜1） |

### Choice

たとえば、メールボックスの振り分けをお願いしてみましょう。受信したメールを state に渡し、どう扱うべきかを 3 択で聞いてみます。

```json
{
  "state": "件名: 【ご請求】9月分の請求書を送付します\n\nお世話になっております。9月分の請求書を添付いたします。お支払い期限は10月末です。ご確認のほどよろしくお願いいたします。",
  "model": "jev-latest",
  "questions": {
    "振り分け": {
      "type": "choice",
      "instructions": "このメールをどう扱うべきか？",
      "criteria": {
        "返信する": "相手が返事を待っている。質問、依頼、日程調整など",
        "あとで読む": "返事は不要だが内容は把握しておくべき。請求書、報告、お知らせなど",
        "無視": "宣伝、自動送信、対応不要の通知"
      }
    }
  }
}
```

`criteria` に書いた説明文が判断の基準になります。返ってくるのは、選んだ選択肢の名前と、それぞれの確率です。

```json
{
  "answers": {
    "振り分け": {
      "type": "choice",
      "choice": "あとで読む",
      "confidence": 0.86,
      "probabilities": {
        "返信する": 0.09,
        "あとで読む": 0.9,
        "無視": 0.01
      }
    }
  }
}
```

`choice` には確率が最も高い選択肢が入り、`probabilities` は全選択肢の確率です。`confidence` は分布がどれだけ一箇所に集中しているかを 0〜1 で表した値で、迷いなく選んだかどうかの目安になります。選択肢は最大 255 個まで指定できます。

### Score

 `criteria` を選択肢のマップではなく、順序のある配列で渡します。たとえば、同じメールに対して「緊急度」を `["急ぎではない", "今週中に対応", "今日中に対応"]` の 3 段階で聞くと、`score` に `0.4` のような確率で重みづけした位置が返ります。段階は 2〜10 個です。

### Noul

 `instructions` に命題を書くだけで、`noul` に真である確率が 1 つ返ります。「相手は返事を求めているか」なら `0.05`、といった形です。この場合はまぁ書いてないと思って良いでしょうね。

3 つの型は 1 回の呼び出しに混ぜられます。同じ state に対してすべての question が並列に、互いに独立して評価されるので、question を増やしても応答時間はほとんど変わりません。公式ドキュメントはこれを前提に、複数の要素を一度に判断させる質問は避けて、要素ごとに分けて聞き、組み合わせはコードのロジックで書くことを勧めています。

## if 文に書けなかった判断が書ける

個人的に、Jev の激アツポイントはここです。

これまで、コーディングによって自動化できたのは、送信元のドメイン、件名に含まれる単語、金額の大小などなど、コードで機械的に判定できる条件だけでした。一方で「相手は返事を待っているか」「この問い合わせは急ぎか」みたいな判断は、人が読めば一瞬で分かるけど条件式には書けないので、結局人が目で見て振り分けなきゃいけなかったんですよね。

でも、Jev があれば話は変わります。

```ts
// 今まで書けた条件
if (mail.subject.includes("請求")) {
  await archive(mail)
}

// 書けなかった条件
if (await jev.noul(mail, "相手は返事を待っているか") > 0.8) {
  await notify(mail)
}
```

条件式の中に Jev の判断を置くだけで、分岐の形も分岐先の処理もそのままです。もちろん LLM でも同じことはできましたが、文章で返ってきた答えを解析する処理が必要で、1 回に数秒かかるし大掛かりだしトークンも使うし、「メールの振り分けに AI を呼ぶのは大げさかなぁ」といってやってませんでした。でもこれなら綺麗にできそうです。

公式ドキュメントが「質問は要素ごとに分けて、組み合わせはコードのロジックで書く」と勧めているのも、この使い方を前提にしているんだろうと思います。「返事を待っているか」「急ぎか」「以前にも連絡があったか」をそれぞれ 1 つの question として聞き、`&&` や `||` でつなぐのは、普段の if 文の書き方そのままです。

## 使い方

呼び出し方は 2 つあります。TypeSafe AI の API を直接叩くか、Cloudflare Workers AI 経由で使うかです。

### TypeSafe AI の API

API キーは [TypeSafe AI のコンソール](https://console.typesafe.ai/settings/keys)で発行できます。公式 SDK は JavaScript と Python があり、JavaScript は `npm install @typesafe-ai/sdk` で入れられます。

```ts
import { choice, noul, score, TypeSafeClient } from "@typesafe-ai/sdk"

const client = new TypeSafeClient() // 環境変数 TYPESAFE_API_KEY を読む

const response = await client.systemOne({
  state: mail,
  questions: {
    振り分け: choice("このメールをどう扱うべきか", {
      返信する: "相手が返事を待っている。質問、依頼、日程調整など",
      あとで読む: "返事は不要だが内容は把握しておくべき。請求書、報告、お知らせなど",
      無視: "宣伝、自動送信、対応不要の通知",
    }),
    緊急度: score("どのくらい急ぎか", ["急ぎではない", "今週中に対応", "今日中に対応"]),
    返事待ち: noul("相手は返事を待っているか"),
  },
})

console.log(response.answers.振り分け.choice)
```

3 つの question を 1 回の呼び出しにまとめて渡しています。`choice` `score` `noul` は question を組み立てる関数で、`answers` の型は渡した question から推論されるので、`response.answers.振り分け.choice` の型は `"返信する" | "あとで読む" | "無視"` になります。

### Cloudflare Workers AI

Workers AI に `typesafe/jev` というモデル ID で載っているので、Cloudflare のアカウントがあれば TypeSafe AI 側の登録なしで使えます。Workers からは AI バインディングで呼びます。

```ts
const response = await env.AI.run("typesafe/jev", {
  state: mail,
  questions: {
    振り分け: {
      type: "choice",
      instructions: "このメールをどう扱うべきか",
      criteria: {
        返信する: "相手が返事を待っている。質問、依頼、日程調整など",
        あとで読む: "返事は不要だが内容は把握しておくべき。請求書、報告、お知らせなど",
        無視: "宣伝、自動送信、対応不要の通知",
      },
    },
    返事待ち: {
      type: "noul",
      instructions: "相手は返事を待っているか",
    },
  },
})

if (response.answers["振り分け"].choice === "返信する") {
  await notify(mail)
}
```

request と response の形は TypeSafe AI の API と同じで、`answers` の下に question ごとの結果が入ります。コンテキストウィンドウは 32,000 トークンです。Email Workers でメールを受け取って、その場で振り分ける、といった組み合わせがそのまま書けます。

## おわりに

ここ数年、AI といえば「文章で会話するもの」でした。Jev はそこを最初から捨てていて、聞かれたことに値だけで答えてくれます。余計なことをしないので、結果として爆速だし安いし想定外の答えがないし、良いことずくめです。AI を組み込んだフローとかもかなり作りやすくなって、今後の AI 活用がまた一つ、大きく変わるような気がしています。

今回はまだ調べただけで使えていないんですが、これから実際に使ってみて楽しもうと思います！！
