内定者向けの交流アプリを 1 人で運用しています。ユーザーは 50 人ほどで、プロフィール、写真、タイムライン、通知があります。

このアプリに、今のところ 1 円も払っていません。その代わり、無料枠を 3 回使い切りました。1 回は本番が完全に停止しました。

この記事は、その 3 回で何が起きたかと、そこから出てきた「無料枠の読み方」の記録です。

## 何を作っているか

技術構成は、途中で丸ごと入れ替えています。

| | 移行前 | 移行後 |
|---|---|---|
| ホスティング | Vercel (Next.js) | Cloudflare Workers |
| 画像 | Supabase Storage | R2 |
| DB | Supabase Postgres | Neon |
| 認証 | Supabase Auth | Better Auth |

移行の理由は、後半で書きます。先に言っておくと、**移行しないと復旧できなかったわけではありません**。復旧はできた上で、移行を選びました。

## なぜ払わないのか

枠を超えたとき、公式に案内される解決策は Supabase Pro の $25/月 でした。学生でも払えない額ではありません。払わなかった理由は、金額ではありませんでした。

- 個人開発なので、そもそも続くかどうかわからない。続くかわからないものに固定費を付けたくない
- 2 人で運営していた。**どちらが払うのか**という話になる

3 つ目が本音で、要するに**払うかどうかを決めるコスト**のほうが $25 より重かった、という話です。この判断自体が良かったかは何とも言えませんが、以下はその前提で読んでください。

# 1 回目と 2 回目: 画像

最初に当たったのは Vercel の画像最適化の枠でした。そして、その回避策が次の事故を作りました。この 2 つは別々の事故ではなく、続き物です。

## 変換した回数で減る

Next.js の `<Image>` を使うと、画像は Vercel 側で最適化されて配信されます。Hobby プランの枠はこうなっています。

| Image Usage | Hobby |
|---|---|
| **Image transformations** | **5,000 / 月** |
| Image cache reads | 300,000 / 月 |
| Image cache writes | 100,000 / 月 |

枠は 3 種類ありますが、先に枯れるのは一番上の **transformations（変換回数）**です。

ここで大事なのは、これが「保存されている画像の枚数」の枠ではないことです。当時アプリが持っていた写真は 204 枚でした。それで月 5,000 の変換枠を使い切りました。

枚数と変換回数がずれる理由は 2 つあります。

**1 枚から複数の variant が作られます。** Next.js の既定値では、幅の候補が `deviceSizes` に 8 種、`imageSizes` に 7 種の合計 15 種あります。フォーマットは既定では WebP のみです（AVIF は既定に入っていません）。つまり 1 枚から最大 15 通りの変換が発生します。

それでも 204 × 15 = 3,060 で、5,000 には届きません。増幅させていたのはもう一方です。

**期限が切れると再変換されます。** transformations はキャッシュの MISS **と STALE** で課金されます。そして `minimumCacheTTL` の既定値は 14400 秒、つまり 4 時間です。同じ画像の同じ幅が、1 日に最大 6 回、変換としてカウントされ得ます。

```
5,000 / 30 日 = 167 変換/日
4 時間 TTL = 1 日 6 スロット → 1 スロットあたり 28 variant で枯れる
```

50 人が毎日開くアプリだと、これは普通に届きます。**枠は「何枚持っているか」ではなく「見られ続けているか」で減っていました。**

超えると、新規の変換が 402 を返して失敗します。既に変換済みの画像は生きたままなので、**一部の写真だけが壊れて alt テキストが表示される**、という分かりにくい壊れ方をします。

## 変換をやめたら、原本を配ることになった

このとき、まず正攻法を試しています。`deviceSizes` と `imageSizes` を絞り、`minimumCacheTTL` を 31 日に延ばしました。これは公式ドキュメントが推奨している対処そのものです。

それでも同じ日に枠が枯れたので、`next/image` を使っている 9 つのコンポーネントに `unoptimized` を付けて、最適化そのものをバイパスしました。画像は Supabase Storage の原本を直接配ることになります。

このときのコミットメッセージにこう書いてあります。

> トレードオフ: 帯域は増える (原本サイズをそのまま配信) が、まず「表示されない」状態を解消するのが最優先。次段で Supabase Storage Transformations へ loader を差し替えるか、Pro プランへ移行するか検討。

帯域が増えることは分かっていましたし、次の手も決めていました。見落としていたのは方向ではなく**速度**です。

**6 日後に本番が止まりました。**

## 保存量ではなく転送量で死ぬ

出たエラーは `402 exceed_cached_egress_quota` でした。Supabase Free の転送枠を使い切っています。

止まったのは画像だけではありません。**Auth も停止して、ログインができなくなりました。** Supabase は同じプロジェクトの枠を全機能で共有しているので、画像の転送量で認証が巻き添えになります。

Supabase Free の枠はこうです。

| 項目 | Free |
|---|---|
| **Cached egress** | **5 GB** |
| File storage | **1 GB** |

当時アプリが持っていた画像は **324 MB** でした。保存枠 1 GB に対して 32% なので、余裕があります。**枯れたのは、隣に書いてある転送枠のほうでした。**

保存量と転送量は別枠です。同じ料金ページに並べて書いてあります。それでも見ていたのは保存量だけでした。

数字で見ると、届いて当然でした。

```
324 MB / 188 枚 = 1 枚あたり平均 1.72 MB
5 GB ÷ 1.72 MB ≈ 2,900 回の画像読み込みで枯れる
```

50 人が 1 か月アプリを開けば、写真の読み込みは 3,000 回に届きます。表示に必要なのは 200〜400px なのに、2〜4 MB の原寸を毎回配っていたので、そうなります。

## 復旧はできた。それでも移行した

このあと、Supabase の organization を自分の名義に移管しました。それで枠が復活し、画像も取り出せるようになりました。**そのまま Supabase を使い続けることもできました。**

移行を選んだのは、構造が何も変わっていないからです。原本を直接配る構成のままだと、転送量はユーザー数にそのまま比例します。試算するとユーザー 160 人前後で再び 5 GB に当たります。**今月を乗り切るのではなく、比例課金から降りることにしました。**

移行先を選ぶ条件は 1 つだけにしました。**転送量で課金しないこと。**これを外すと同じ死に方をします。

この条件を満たすオブジェクトストレージは実質 R2 と Backblaze B2 くらいで、Workers と同居できてバインディングで直接叩ける R2 に決めました。R2 には**転送量という枠がそもそも存在しません**。DB 側は Postgres 互換で書き換えずに移せることを理由に Neon にしました。

同時に、画像の最適化を**アップロード時**に移しました。

```
移行前: リクエスト時に変換 → 見られるたびに変換回数が減る → 回避すると原寸配信になる
移行後: アップロード時に 1 回だけ変換 → 配信は R2 なので転送量は無料
```

ブラウザ側で 1024px の WebP に縮小してから送るので、サーバーは受け取ったものを置くだけです。変換回数という課金経路自体が消えました。

## 対策を入れたことと、対策が効いていることは別

後日、R2 の中身を全部読んで形式を数えたところ、こうなっていました。

```
形式    件数    合計MB   平均KB
PNG      18     29.9     1,661   ← .webp という名前の PNG
WEBP    186     23.5       126
```

`canvas.toBlob(cb, "image/webp", q)` は、**WebP のエンコードに対応していないブラウザでもエラーを出さず PNG を返します**。仕様どおりの挙動で、呼び出し側は成功したと判断します。

1024px の PNG は可逆圧縮なので 1.5〜3 MB になり、元の JPEG より大きくなることさえあります。**縮小したのに軽くならず、画質だけ落ちる**という結果になっていました。移行後の新規アップロードだけで見ると、失敗率は 56% でした。

このコードは初期からあり、自分も 2 回触っています。誰も気づきませんでした。silent failure なので当然ではあります。

気づけなかった理由はもう 1 つあります。**R2 は転送量が無料なので、これは請求に一切出ませんでした。**困っていたのは iPhone ユーザーの表示が遅いことだけです。

修正は、戻ってきた Blob の `type` を確認して、WebP でなければ JPEG で取り直すだけでした。

```ts
canvas.toBlob((webp) => {
  if (webp?.type === "image/webp") return resolve(webp);
  // webp 非対応 → PNG が返ってきている。JPEG で取り直す
  canvas.toBlob((jpeg) => resolve(jpeg ?? webp), "image/jpeg", 0.82);
}, "image/webp", 0.8);
```

形式を指定する API は、指定が通ったかを戻り値で確認する必要があります。そして**無料枠が広いと、壊れていても気づく機会がありません**。

# 3 回目: DB とキャッシュ

移行して、画像の問題は片付きました。次は DB の枠に当たりました。

## 使っていない時間に払っていた

Neon Free の枠は容量ではなく**時間**です。

> Free plan: 100 CU-hours / project / month
> — enough to run a 0.25 CU compute for 400 hours/month
> Scale-to-zero: always enabled (5 min idle timeout), can't be disabled

Neon は 5 分アクセスがないと compute を停止します。**Free ではこれを無効化できません。**停止した状態で最初のクエリが来ると、起動を待つことになります。体感で 10〜30 秒でした。

なので、cron で 5 分おきに `SELECT 1` を打って起こし続けました。深夜は不要なので、時間帯は絞りました。

```
*/5 22-23,0-14 * * *   (UTC / JST 7:00〜24:00)
```

絞る判断自体は間違っていません。間違っていたのは、**桁を一度も計算していなかった**ことです。

```
100 CU-h ÷ 0.25 CU = 400 時間/月 が予算
400 h ÷ 30 日      = 13.3 時間/日

書いた cron       = 17 時間/日
17 h × 30 日      = 510 時間 = 127.5 CU-h  → 予算の 127.5%
```

無料枠の中に収める工夫のつもりで書いたものが、単体で予算を 27% 超えていました。

## 誰も使っていない環境が、本番と同じだけ使っていた

さらに悪いことがありました。`wrangler.jsonc` の `triggers` は、環境ごとの設定に**継承されます**。

`r2_buckets` や `kv_namespaces` や `vars` は `env.preview` に書かないと引き継がれません。`triggers` はその例外で、何も書かなければ本番と同じ cron が preview でも動きます。

実測がこれです。

| branch | active_time | CU-h |
|---|---|---|
| production | 185.8 h | 46.76 |
| dev（誰も使っていない） | 180.6 h | 45.73 |
| **合計** | | **92.49 / 100** |

**誰も開いていない preview が、本番の 97.8% を消費していました。**枠の半分は、存在を忘れていた環境が使っていたことになります。

## 速くすることと、寝かせること

cron を書いた動機は「速くするには起こしておくしかない」でした。これが思い込みで、実際には両立できます。やったことは 3 種類に分かれます。

**1. そもそも DB を叩かない**

- タイムラインは全員に同じ内容を返すので、Cloudflare の edge に 1 時間キャッシュして全員に配れます。キャッシュに当たれば DB には行きません
- セッションの検証で毎回 DB を引いていたのをやめ、署名付き cookie で判定するようにしました。ここも DB に行きません

**2. DB は起きるが、待たせない**

- プロフィールや未読数は人によって違うので、共有キャッシュには載せられません。ここは Service Worker のキャッシュで前回の内容を即座に表示して、裏で取り直します。DB は起きますが、ユーザーは待ちません

**3. 使っていない時に起こさない**

- cron を止めました
- 新着通知の 60 秒ポーリングを廃止し、タブに戻ってきたときだけ取りに行くようにしました
- 通知の即時性は Web Push が別経路で担保しているので、ポーリングは無くても困りません

結果として、ユーザーから見た速度は保ったまま、誰も使っていない時間は DB が寝るようになりました。

## commit しただけでは止まらない

cron を止めるコミットを入れた数日後、消費が止まっていないことに気づきました。

| | |
|---|---|
| cron 停止のコミット | 2026-08-12 |
| 本番の最終デプロイ | **2026-08-06** |

`wrangler.jsonc` の `triggers` はデプロイして初めて反映されます。**コミットはしていましたが、デプロイしていませんでした。**

そのときの消費ペースがこれです。

```
04:04Z   92.49 CU-h
07:14Z   93.87 CU-h   → +1.38 / 3.2h = 0.435 CU-h/時
残り 6.13 CU-h ÷ 0.435 ≈ 14 時間で枯渇
```

枯渇すると次の請求期間まで compute が止まります。つまり、また本番が止まります。残り 14 時間でした。

`wrangler triggers deploy` を本番と preview の両方で叩いて、12 分後の再計測で増加が 0.000 になったことを確認しました。

# 3 回とも同じ形をしていた

並べてみると、全部同じでした。

| | 枠の前提 | 壊し方 |
|---|---|---|
| 1 | 変換した分だけ課金する | **配信のたびに**変換させた |
| 2 | 配ったバイト分だけ課金する | **原寸を**配った |
| 3 | 起きていた時間だけ課金する | **使っていない時も**起こした |

**一度も「枠が小さかった」ということはありませんでした。**毎回、枠の前提と噛み合わない実装をしていただけです。無料枠は「使った分だけ」で設計されていて、それを「使っていない時も使う」実装で殺していました。

## 無料枠は「何で絞るか」で読む

ここから出てきた読み方が 1 つあります。無料枠は「何をタダにしてくれるか」ではなく、**何を単位に減るか**で見るということです。

| | 絞りどころ |
|---|---|
| Vercel Image Optimization | 変換した**回数** |
| Supabase | 転送した**量** |
| Neon | 起きていた**時間** |
| R2 | 保存している**量**だけ |

どのサービスも同じものをタダにはしてくれません。だから移行とは「**絞りどころを乗り換えること**」で、前のサービスでは気にしなくてよかったものが、移った先で突然コストになります。実際、画像の転送量を無料にした先で、DB の稼働時間という枠に当たりました。

逆に言えば、自分のアプリで**何が増えるのか**が分かっていれば、どの枠に当たるかは先に予測できます。

- 変換回数は、コンテンツの**種類数**に比例します。ユーザー投稿があると増えます
- 転送量は、**閲覧数**に比例します。人が増えると増えます
- 稼働時間は、**開かれている時間**に比例します。ポーリングを書くと増えます
- 保存量は、どれにも比例しません

今も $0 で動いています。悪あがきは続いています。
