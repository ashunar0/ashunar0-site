## はじめに

前回、tl;dv で起きたことの事実関係をまとめました。この記事はその続きで、なぜこの構成だと事故が見えなくなるのかを整理します。

https://ashunar0.dev/posts/tldev-insident/

Firestore や Supabase のような BaaS では、ブラウザから DB の API へ直接クエリが飛びます。アプリのコードを一行も通らずにデータへ到達できる、ということです。

この構成では、脆弱性がコードに現れません。認可は DB 側の設定ファイルに置かれ、そこに何も書かなければ「何も書いていない」という不在として存在します。grep しても出ず、差分にも現れず、型検査も lint も走りません。読んで見つけられない脆弱性です。

tl;dv はこれで 181,874 件の会議を露出させました。4つのコレクションのうち3つは正しく守られていて、1つだけが落ちていました。

## テナントが混ざっているという前提

SaaS は1つの DB に全顧客のデータを混ぜて格納します。tl;dv であれば、1つの `meetings` コレクションに全社の会議が同居しています。

```
meetings/
  ├ meeting_001  { ownerEmail: "asahi@company-a.jp", conferenceId: "abc-defg-hij" }
  ├ meeting_002  { ownerEmail: "bob@company-b.com",  conferenceId: "xyz-1234-567" }
  └ meeting_003  { ownerEmail: "gov@example.gov",    conferenceId: "..." }
```

物理的には同じ棚に並んでいます。顧客ごとに分かれて見えるのは、取り出すときに絞っているからであって、置き方が分かれているからではありません。この「自分のものだけに絞る」仕組みがテナント分離です。

ここが後で効いてきます。棚に直接手を伸ばせる立場からすると、絞りが効かなかったときの既定値は「全顧客」です。認可を一つ落としたときに、漏れるのが一件分ではなく全件になるのは、このためです。

## 攻撃面がコードの外にある

サーバーを挟む構成では、外から到達できる場所と、開発者が書いたコードが一致します。`app.get('/meetings', ...)` を書いたから `/meetings` が生まれる。書かなければ存在しない。攻撃面は grep で列挙できます。

BaaS では、この一致が崩れます。到達できる場所を決めるのはデータの形であって、アプリのコードではありません。

```typescript
const q = query(collection(db, 'meetings'), where('ownerEmail', '==', myEmail))
```

この `where` は絞り込みであって制限ではありません。ブラウザのコードは誰でも書き換えられるので、外せば全件返ります。

さらに SDK すら要りません。実体はただの HTTPS API なので、トークンさえあれば直接叩けます。

```bash
curl 'https://firestore.googleapis.com/v1/projects/{project}/databases/(default)/documents/meetings' \
  -H "Authorization: Bearer $TOKEN"
```

つまり、フロントのコードがどれだけ正しくても関係ありません。**フロントのコードは仕様書であって、防御壁ではありません。**

そして開かれているのは、開発者が書いた1本のクエリではなく、`meetings` に対する任意のクエリです。全件取得も、他人の文書の直接参照も、任意フィールドでの検索も含まれます。

守るのは Security Rules（Supabase なら RLS ポリシー）だけです。DB 側の設定ファイルに、こう書きます。

```javascript
match /meetings/{meetingId} {
  allow read: if request.auth != null
              && resource.data.ownerId == request.auth.uid;
}
```

## 見えない、とはどういうことか

同じ「認可が抜けている」でも、構成によって見つかりやすさがまったく違います。

| | 認可が抜けたとき |
|---|---|
| サーバー経由 | 欠陥は書いたコードの中にある。該当の関数が差分に出る。読めば見つかる |
| DB 直結 | 欠陥は設定ファイルの不在として存在する。差分に出ない。読んでも見つからない |

サーバー側の認可漏れは「間違ったものを作った」です。作った以上そこにコードがあり、レビューの対象になり、テストを書く場所があります。

BaaS の認可漏れは「作らなかった」です。存在しないものはレビューできません。型検査も lint も、書かれたコードを検査する道具なので、書かれなかったものには反応しません。

しかも Firestore では、守るべき対象の一覧すら取れません。コレクションはドキュメントを書いた瞬間に実行時に生えるもので、スキーマ宣言もマイグレーションもありません。「全コレクションにルールがあるか」を確かめようにも、全部が何なのかがどこにも書かれていません。

Supabase の RLS はもう一段危ない性質を持っています。**`ENABLE ROW LEVEL SECURITY` を打っていないテーブルは、ポリシーを書いてあっても素通りします。** 有効化とポリシー定義が別ステップなので、片方だけやって安心する事故が起きます。

## 典型的な失敗：書いたのに守っていない

見えないのは不在だけではありません。ルールが書いてあっても、それが何も守っていないことがあります。

Firestore のデフォルトは全拒否なので、開発中は何も動きません。そこで大抵こう書きます。

```javascript
allow read, write: if request.auth != null;   // とりあえずログイン必須に
```

これで**開発中は完璧に動いてしまいます**。自分のアカウントでしかテストしないため、他人のデータが見えることに気づく機会がありません。そのまま本番へ、というのが黄金パターンです。

`request.auth != null` は「認証されているか」しか見ておらず、「そのデータの持ち主か」を一切見ていません。認証と認可の取り違えです。ルールとしては存在するので、なおさら目に留まりません。

tl;dv の事故はまさにこれです。`users` `transcripts` `recordings` には持ち主を確認するルールが入っていて、`meetings` だけが緩いまま残っていました。原典は「`meetings` にルールが無かった」と書いていますが、既定が全拒否である以上、実際には読める条件のルールが残っていたと見るのが自然です。

**チームは仕組みを理解していて、1つだけ揃えそこねた**わけです。知識不足では説明のつかないタイプの事故だという点が重要です。

## 設計の勘所：認可をデータの形に埋める

ルールを1つずつ手で書くと、書き漏らしが必ず出ます。パス設計で構造的に効かせるほうが確実です。

```javascript
// フラット構造 → ドキュメントの中身を見に行く必要がある
match /meetings/{meetingId} {
  allow read: if resource.data.ownerId == request.auth.uid;
}

// 階層構造 → 一行で配下すべてに効く
match /users/{uid}/meetings/{meetingId} {
  allow read: if uid == request.auth.uid;
}
```

後者はテナント境界がパスそのものに現れているため、ルールを落とす余地が小さくなります。**境界をデータの形に持たせる**という発想です。

## 対策

- **公開してよいデータだけ**クライアント直結にする（プロフィール画像、公開記事など）。機微なものは Edge Functions や Cloud Functions を挟む
- テナント境界を **E2E テストで固定する**。アカウントを2つ作り、片方から相手のデータが取れないことを assert する。この1本で恒久的に守れる
- Supabase なら「RLS 未有効のテーブルが存在しないこと」を CI で検査する

3つ目まで含めて、要点は「人間の目に頼らない」ことです。tl;dv のチームは仕組みを理解していて、それでも落としました。見えないものはレビューでは見つかりません。

## 副次的な教訓：メタデータの分類

tl;dv は「漏れたのはメタデータのみで、録画も文字起こしも無事」と説明しました。しかし `meetings` ドキュメントには `conferenceId` が入っていました。これは実質 Google Meet や Teams の部屋の鍵で、進行中の会議に招待なしで入れてしまいます。

**中身は守られていたが、中身に入るための鍵がメタデータ側に置いてあった**わけです。データを機微 / 非機微で分類するとき、こうした capability を持つ値を非機微側に置くと、分類そのものが崩れます。ID を「推測できないから安全」として扱わないこと、が実務上の教訓です。

## 使わないほうがいい場面

- テナント境界が複雑な業務アプリ → ルールで表現しきれず、結局サーバーを書くことになる
- 監査ログや課金など、書き込みの正しさが要るもの → クライアントを信頼できない
- 権限が動的に変わるもの（招待、共有、ロール変更）→ ルールが肥大化して読めなくなる

逆に、公開データの配信や、ユーザーが自分のデータだけを触るシンプルな構造には素直にはまります。

## おわりに

BaaS は「バックエンドを書かなくていい」ことが売りですが、実際に消えているのは**バックエンドの記述**であって、**認可の責務**ではありません。責務は宣言的な設定ファイルへ引っ越しました。そして引っ越した先では、責務を果たしていないことが何の形にもなりません。

サーバーを一枚挟む構成では、到達できる場所がルーティングに全部書いてあります。地味ですが、**数えられる**ことが効いています。

BaaS を選ぶかどうかの分岐点は、速度と引き換えに「自分の書いたコードを読んでも安全性を確認できない」状態を受け入れられるか、という一点です。
