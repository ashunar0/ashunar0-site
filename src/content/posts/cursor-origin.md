## はじめに

Cursor が 2026 年 8 月 17 日、コードホスティング「Origin」の初期ベータを公開しました。リポジトリ、プルリクエスト、コード閲覧、GitHub 同期が Cursor の中に入ります。全有料プラン（Pro / Teams / Enterprise）で段階的にロールアウトされ、無料プランは対象外です。

構想自体は 6 月の自社カンファレンス Compile で発表されていて、そのときの説明と、いま実際に触れるものの間には距離があります。両方を分けて整理します。

## 何ができるか

Cursor に **Codebase タブ**が増えます。ここが Origin リポジトリの置き場です。

新規リポジトリを作ると、CLI の入れ方と、clone / push のコマンドが出ます。リモートは通常の HTTPS の Git リモートです。

```bash
# 新しく作った空のリポジトリを取ってくる
git clone https://origin.cursor.com/{owner}/{repo}.git

# 手元のプロジェクトを Origin に向ける
cd your-project
git remote add origin https://origin.cursor.com/{owner}/{repo}.git
git push -u origin main
```

Git 互換なので、既存のツールチェーンはそのまま動きます。Cursor のエージェントに頼めば、CLI のインストールからサインイン、リポジトリ作成、リモート設定、push までまとめてやらせられます。エージェントの権限は依頼した本人のアカウント権限に従います。

リポジトリごとにプルリクエストがあり、タイムライン、コミット、チェック、変更ファイルが見られます。差分にコメントを付けてマージするところまで Cursor の中で完結します。

外部連携は現時点で 3 つです。Vercel を繋ぐと PR ごとにプレビューデプロイが付き、CI は Depot と Buildkite に対応しています。

## GitHub ミラーの挙動

一番判断に効くのがここです。既存の GitHub リポジトリを Origin に取り込めますが、**移行ではなくミラー**です。

同期されるもの:

- Git の履歴、ブランチ、タグ
- コード（Origin 上で閲覧・検索できる）
- プルリクエスト（双方向）

同期されないもの:

- Issues
- GitHub Actions のワークフローとシークレット
- CI 設定

プルリクエストの双方向というのは、Cursor 側で書いたコメントが GitHub に投稿され、GitHub 側での返信やリアクションが数秒で Cursor に出る、という意味です。

そして push の行き先です。ミラーしたリポジトリでは **GitHub が source of truth のままで、Origin への push は GitHub に転送されます**。Origin に溜まるのではありません。ミラーを解除して初めて Origin が唯一の実体になります。

つまり初期ベータのミラーは、乗り換えではなく**読み書きの窓を増やす**ものです。既存のワークフローを壊さずに試せる代わりに、GitHub をやめることにはなりません。取り込みには GitHub 側の admin 権限が要ります。

## 6 月に語られた設計目標

Compile での Origin の説明は、いま触れる機能一覧とはかなり毛色が違います。前提として置かれていたのは、**Git ホスティングの負荷特性が人間基準からエージェント基準に変わる**という読みです。

エージェントが並列で動く環境では、clone と push の頻度が人間の比ではなくなり、同じファイルに触る並列ブランチのマージ衝突が常態になります。Cursor が挙げた数値は、単一リポジトリで毎秒 22.6 コミット、毎時およそ 296,000 clone と 81,000 push、グローバル同期は 400 ミリ秒未満というものでした。あわせて、各エージェントの変更意図を読んで自動でマージ衝突を解決するエンジンも示されています。

いずれも Cursor 自身が示した数値と主張で、第三者の検証があるわけではありません。技術的な土台は 2025 年 12 月に買収した Graphite（スタックド PR のレビューツール）を作り直したものだとされています。

初期ベータに入っているのは、この構想のうち土台部分です。自動衝突解決のようなエージェントネイティブな機能はまだ来ていません。

## GitHub との差をどう見るか

現時点で Origin が GitHub にできて GitHub にできないことを持っているわけではありません。むしろ Issues も Actions も無い分、機能は少ないです。

差が出るとすれば置き場所です。コード、PR、エージェントが同じアプリの中にあると、レビュー中の PR に対してそのままエージェントに質問し、修正させてブランチに push させる、という往復がタブをまたがずに済みます。GitHub でも同じことは Cursor から操作すればできますが、そのたびに外部サービスの API を経由します。

一方で預ける先が増えることは事実です。ソースコードのホスティング先が編集ツールのベンダーと同じになるので、組織で使う場合は判断が要ります。Enterprise では管理者がオプトアウトできます。

なお公開が GitHub の障害と重なったことが話題になりましたが、ミラーの push が GitHub に転送される以上、初期ベータの Origin は GitHub 障害時の避難先にはなりません。

## おわりに

初期ベータで確認できるのは、Git 互換のホスティングと、GitHub と共存するミラーと、Cursor 内で閉じる PR レビューまでです。ここまでは既存のフォージと機能で戦うものではなく、Cursor に居続けられる範囲を広げるものと見るのが正確です。

賭けの部分は 6 月に示された前提のほうにあります。エージェントが書く量が人間の書く量を超えたとき、Git ホスティングに要求される性能と衝突解決が今と同じでいいのか。それが本当に効いてくるかどうかは、自動衝突解決が出てから判断することになります。

試すコストは低いです。ミラーは GitHub を source of truth に残したまま張れるので、既存リポジトリを 1 つ繋いで PR の往復を見てみるのが手早いです。
