## はじめに

2026年8月末にZod 4.5がリリースされました。目玉は`z.compile()`で、スキーマをコンパイルすることで、parseがなんと**最大9倍**も速くなるとのこと！

```ts
const Player = z.object({
  username: z.string(),
  bio: z.string(),
  xp: z.number(),
});

const CompiledPlayer = z.compile(Player);
CompiledPlayer.parse({ ... }); // ~9x faster
```

いやじゃあ今まで何にそんな時間かかってたんだよ、って思ったので調べてみたら、そもそも自分がZodのparseを雑にしか理解していなかったことがわかったので、そこから順に整理します。

## parse 1回に含まれる2つの仕事

前提として、parseに届くデータは毎回違います。1回目のリクエストが正しくても2回目が正しい保証はないので、検証そのものはparseのたびに必ず必要です。ここはどんな実装でも省けません。

では`z.compile()`は何を省いたのか？鍵は、parse 1回分の仕事が実は2種類に分かれることです。

- **データを見る仕事** — 「`input.username`はstringか？」という実際のチェック。毎回必要
- **スキーマを読む仕事** — 「このスキーマのキー一覧は？各キーの型は？その型のチェック関数はどれ？」という下調べ。**スキーマが変わらない限り、本来は1回で済む**

これまでのZodは、parseのたびにこの両方をやっていました。イメージとしてはこうです（実際のソースではなく擬似コードです）。

```ts
// parseのたびにこれが動く
for (const key in schema.shape) {          // キーを列挙
  const childSchema = schema.shape[key];   // スキーマを読む
  childSchema._parse(input[key], ctx);     // 汎用関数を呼び、その中でやっとデータを見る
}
```

スキーマという設計図を、実行のたびに読み解きながら動くインタープリタ方式です。汎用的で何でも扱える代わりに、ループ・スキーマの読み取り・関数呼び出しのオーバーヘッドを毎回払います。100万回parseすれば、1ミリも変わっていないスキーマを100万回読み直すことになります。

## z.compile()：スキーマを読む仕事を1回に畳む

`z.compile()`は、スキーマを**一度だけ**読んで、そのスキーマ専用のベタ書きJavaScriptを`new Function()`で生成します。たとえば`{ x: number, y: number }`のスキーマからは、こういうコードが生成されます。

```js
if (typeof input !== "object" || input === null) return false;
if (typeof input.x !== "number") return false;
if (typeof input.y !== "number") return false;
return true;
```

以降のparseで動くのはこれだけです。ループ・スキーマの読み取り・動的な関数呼び出しすべて排除し、純粋にデータを見る仕事だけが残ります。しかもV8のようなJSエンジンは、この手の単純な分岐の並びを機械語レベルまで最適化するのが得意なので、残った仕事自体も速く回ります。

「検証は毎回必要だが、スキーマの解釈は毎回不要だよね」を体現したのが`z.compile()`だったんですね。

### なお挙動は変わらない

速くなる代わりに何か犠牲になっていそうですが、APIも型推論もエラーメッセージも一切変わりません。これはfast-path方式で担保されています。

生成コードがやるのはあくまで「validかどうか」の高速判定だけで、invalidだった場合は従来のパーサーにフォールバックして、いつもどおり詳細なZodErrorを組み立てます。エラーを組み立てる複雑な部分はコンパイルの対象外にして、正常系だけを最速にしてくれるわけです。Zodのテストスイート自体が通常版とコンパイル版の2周走っていて、挙動の一致が保証されています。

## じゃあなんで今までやらなかったの？

さて、ここまで読むと、毎回スキーマを読み直すのは明らかに無駄なわけで、最初からこうすればよかったのでは...？と感じてしまいます。

実際、この手法自体は新しくありません。ajvは2015年頃からずっと同じ方式（スキーマから`new Function()`でコードを生成する）ですし、typiaやTypeBoxのTypeCompilerもそうです。当然Zodが知らなかったはずがなく、わかった上でやらない判断をしていた、というのが妥当な推論でしょう。

個人的には、やらない理由は2つあったと考えています。

### 1. `new Function()`が実質evalであること

eval禁止のCSP環境では実行時エラーになるので、ライブラリの**デフォルト動作**にすると「環境によっては動かないバリデータ」になってしまいます。実際Zod 4は内部の一部で同種のコード生成をすでに使っていて、CSP環境でエラーになる報告が上がり、`z.config({ jitless: true })`という逃げ道が用意された経緯があります。デフォルトを安全側に倒すのはライブラリとして合理的な判断です。


### 2. 挙動の完全一致を保つコスト

Zodの売りは詳細なZodError、refine、transform、asyncサポートといった柔軟さで、これを生成コードで1つも違えず再現しようとすると、パーサーと同じものをコード生成器としてもう1つ実装して、両方を永久にメンテすることになります。バグれば「コンパイルすると挙動が変わる」という最悪の壊れ方をします。

### じゃあなぜ今できたのか?

大きいのは、さきほどのfast-path方式という設計だと思います。生成コードの仕事を「validかどうかの判定」に限定してinvalid時は従来パーサーへ丸投げする、と決めたことで、エラー組み立てという一番複雑な部分を再実装せずに済むようになりました。これにより、2つ目のコストがこれで大きく下がっています。

1つ目のCSP問題は、コンパイルをopt-inにすることで解決しています。`z.compile()`の明示呼び出しか`import "zod/compile"`の1行を書いた人だけが対象なので、自分の環境で`new Function()`が使えるかはユーザーが判断できます。デフォルトの挙動は何も変わりません。

土台の話もあります。Zod 4は内部をゼロから書き直したメジャーバージョンで、スキーマの内部表現が機械的に辿ってコード生成できる作りになったのはこのときです。逆にいうと、Zod 3の構造のままでは作れなかった機能でもあります。

## 使い方

個別にコンパイルするか、アプリ全体に効かせるかの2通りです。

```ts
// 1. 個別に明示コンパイル
const CompiledPlayer = z.compile(Player);

// 2. グローバルモード：エントリポイントで1回importするだけ
import "zod/compile";
```

グローバルモードは、以降に定義された全スキーマが初回parse時に自動でコンパイルされます。lazyなので、実際にparseされたスキーマだけがコンパイル対象です。`node --import zod/compile app.js`のように起動オプションでも有効化できます。なおこれはアプリケーション用で、ライブラリが仕込むものではないと明記されています。

## どのくらい速いか

公式の数字をいくつか挙げます。

- 55スキーマのベンチマークで中央値2.4倍。複雑なスキーマほど伸びて、object/array系で3〜9倍
- 20キーのobject: 301ns → 38ns
- Moltarベンチマークで47.5M ops/秒。ビルドステップ前提のコード生成系であるtypia（45.3M）とほぼ互角

最後のが今回の本命だと思っています。これまで実行速度が欲しい場面では、TSコンパイラへのプラグインが必要なtypiaや、独自スキーマ言語のajvといったコード生成系を選ぶ必要がありました。「DXならZod、速度ならtypia」というトレードオフです。4.5はそれをビルドステップなし・設定なし・API完全互換で消しにきました。

一方で、1回のparseが数百ns → 数十nsという話なので、効くのは高トラフィックなAPIサーバーや大量データのバッチ処理のように、parseが積み重なる場所です。DBクエリに10msかかるエンドポイントや、低頻度なフォームバリデーションでは体感差は出ないかもしれません。

## 注意点

いくつか把握しておくべき制約があります。

### CSP環境では動かない
`new Function()`は実質evalなので、eval禁止のContent Security Policy下ではコンパイルできません。`z.config({ jitless: true })`でグローバルモードは自動的に無効化されます。コンパイルに失敗しても例外にはならず、スキーマは非コンパイルのまま返って従来どおり動きます。

### コンパイルできないスキーマがある
非同期のrefine/transform、再帰スキーマ、`z.coerce.*`などが対象外です。ただしobjectの子の一部だけが非対応の場合、その子だけフォールバックして親はコンパイルされたまま、という部分コンパイルをしてくれます。黙ってフォールバックされると困る場合は`z.compile(Schema, { strict: true })`で例外にできます。

### 派生を作り終えてからコンパイルする
`z.compile(z.string().refine(...))`が正しく、`z.compile(z.string()).refine(...)`の順ではコンパイルの恩恵が受けられません。

### invalidな入力は逆に2回分のコストを払う
fast-pathで弾かれてからフォールバックが走るためです。届くデータの大半がinvalidなワークロードでは旨味が減ります。

## まとめ

`z.compile()`は、parseに含まれる「データを見る仕事」と「スキーマを読む仕事」のうち、後者を初回1回に畳む機能でした。検証は毎回必要ですが、変わらないスキーマを毎回読み直す必要はなかった、というシンプルな話です。

導入はimport 1行、挙動は完全互換、失敗しても静かに元の方式で動きます。効く場所は限られるものの、リスクがほぼないので、サーバーサイドでZodを使っているならとりあえず試してみる価値はありそうです。
