## php2shell ってなに？

タイムラインを見ていたら、PHP がなんだかかなり大変なことになっているようです。React や Rails でも似たような脆弱性はあったんですが、今回はなんだか騒ぎ方も規模も違います。なんと高市総理まで注意喚起していました。さすがに今まで見たことがない緊急性であることは間違いなさそうです。

https://x.com/takaichi_sanae/status/2112890642590564386?s=20

php2shell は、PHP 本体に見つかった 2 つの脆弱性（CVE-2026-109618 と CVE-2026-109619）の通称です。認証を通さず外からサーバー上の任意のコードを実行できてしまうというもので、深刻度は CVSS v4.0 で 9.2 です。

困ったことに、修正版が出る前に脆弱性の情報が漏れてしまいました。Cloudflare の CTO によると、修正版が出る前から攻撃も始まっていたそうです。修正版が出たのは日本時間の 10 月 21 日の 23 時ごろで、それまでは確実に防ぐ方法がありませんでした。

修正版は PHP 8.5.12、8.4.27、8.3.36、8.2.35 です。これより前のバージョンは全部対象で、PHP-FPM、Apache の mod_php、FrankenPHP など、Web のリクエストを受けている PHP ならどれも危ないとされています。

イギリスのセキュリティ機関（NCSC）は、「すぐ更新できないならシステムをオフラインにしてください」とまで呼びかけています。当方 PHP はほとんど触ったことがなく、今回の事態にあまり実感を持てていません。去年の React2Shell などではここまで大ごとではなかったような気がしますが、いったい何があったのでしょうか... 

## なんでこんなに大騒ぎなの？

調べてみると、理由は大きく 2 つありました。PHP を使っているサイトが多すぎることと、修正版より先に情報が漏れてしまったことです。

### PHP を使っているサイトが多すぎる

W3Techs の集計では、サーバー側の言語が分かるサイトのうち、約 7 割が PHP で動いています。2 位の Ruby と JavaScript が 7% 前後なので、ほぼ一強です。そんなに使われていたんか...

この数を押し上げているのは WordPress です。WordPress だけで、全 Web サイトの約 4 割を占めています。個人ブログやお店のサイト、会社や自治体のホームページまで、エンジニアじゃない人がサイトを作るときの定番ですもんね。Laravel はサイトの数こそ WordPress よりずっと少ないですが、業務システムや Web サービスの裏側でよく使われています。顧客データや決済を抱えていることも多いです。

しかも今回の穴は PHP 本体にあるので、WordPress でも Laravel でも、アプリ側の作りに関係なく対象になります。PHP がリクエストを読み込む段階で攻撃が成り立つので、アプリ側で防ぐこともできません。React2Shell は React Server Components を使っているアプリだけが対象でした。Rails の件（CVE-2026-66066）も、Active Storage で画像を受け付けていて、しかも古い libvips を使っているときだけです。条件の絞られ方がまるで違います。

### 修正版より先に情報が漏れた

ふつうは「穴が見つかる → 修正版が出る → 攻撃が始まる」の順に進むので、攻撃が来る前に修正版を当てる時間があります。Rails の件も、修正版が出たのは 7 月 29 日で、攻撃が報告されたのはその約 1 か月後でした。

今回は「情報が漏れる → 攻撃が始まる → 修正版が出る」の順になってしまいました。直し方が配られる前に、攻撃する側はもう動いていました。

なんで先に漏れたのかというと、これがなかなかお粗末な話でした。本来は PHP の開発チームとセキュリティ企業のあいだで、10 月 22 日までは詳細を公表しない取り決めになっていました。ところが 10 月 20 日の朝、Hacker News に「PHP の重大な脆弱性が 2 件、もうすぐ公開される」という投稿が出てしまいます。投稿はすぐ消されましたが、スクショが SNS で出回りました。

その数時間後に、セキュリティ企業の watchTowr が「脆弱性は本物で、こちらでも再現できた」と認めました。これを受けて PHP 側は、修正版の公開を 1 日前倒ししています。ちなみに「php2shell」という呼び名も、PHP 公式が付けたものではなく、漏れた資料のほうから来たものだそうです。

|  | React2Shell | Rails の件 | php2shell |
| --- | --- | --- | --- |
| 対象 | RSC を使うアプリ | 条件がそろった Rails アプリ | PHP で動くもの全部 |
| 順番 | 修正版 → 攻撃 | 修正版 → 約 1 か月後に攻撃 | 情報漏れ → 攻撃 → 修正版 |
| アプリ側の対策 | できる | できる | ほぼできない |

どっちか片方だけなら、「大きめのニュース」くらいで済んだのかもしれません。対象が多いうえに直す時間もないので、「今夜中に対応して！」という大騒ぎになっていたんですね。

## じゃあどうすればいいの？

PHP を使っているなら、とにかく修正版をすぐ当てるしかありません。

ただ、これは今回だけの話ではなさそうです。最近は、9 月のタイムズカー（約 660 万件）をはじめ、個人情報が流出したというニュースを本当によく見かけます。AI のおかげで開発が簡単になったのと同じように、穴を探したり攻撃したりするのも簡単になってきているんだと思います。今回のような脆弱性や攻撃は、これからもどんどん出てくるはずです。

なので、次に備えて今回の件から学べそうなことを考えてみました。

### 言語を変えても防げない

言語を乗り換えても、この手のリスクはほとんど減らないようです。Java には 2021 年の Log4Shell、JavaScript には React2Shell、Ruby には今年の Rails の件がありました。同じくらいの事故は、どの言語でも起きています。

TypeScript に移ったとしても、npm のパッケージがたくさん入るぶん、穴の入り口はむしろ増えるかもしれません。書き直しの途中で新しいバグが入ることも考えると、脆弱性を理由に移行するのは割に合わなさそうです。

移行に意味があるのは、修正版が出なくなった古いバージョンに取り残されたときです。今回も、PHP 8.1 以前は公式の修正版が出ていません。あまりに深刻なので、7.4〜8.1 向けに最小限の修正コードだけは配られましたが、自分でビルドする人向けの救済措置です。問題は言語よりも古さのほうにあります。

### すぐ更新できる状態にしておく

どの言語でも穴はいつか見つかるので、差がつくのは見つかってから直すまでの速さです。今回は「修正版が出てから 15 分で大規模な攻撃が始まる」という予想まで出ています。

更新には 2 種類あります。Rails の 8.0.5 → 8.0.5.1 のようなセキュリティ修正だけの小さい更新と、Rails 7 → 8 のように書き方が変わる大きい更新です。今回の PHP も小さい更新なので、サポート中のバージョンならすぐ当てられます。

ただ、大きい更新をサボって古いメジャーバージョンに残り続けると、いつか小さい更新が出なくなります。今回の PHP 8.1 以前がまさにこの状態です。大きい更新を回せるかどうかが、そのまま緊急時に間に合うかどうかを決めます。

大きい更新を楽にするために、作る段階からできることもあります。

- テストを書いておく。上げたあとに何が壊れたかがすぐ分かる
- 業務のロジックをフレームワークの都合と混ぜない。更新で直す場所が境目だけで済む
- 依存するパッケージを絞る。1 つでも新しい版に対応していないと、そこで止まる
- こまめに上げる。1 回あたりの差が小さければ、そこまで大変にならない

あとは、入られたときの被害を小さくしておくことも大事です。要らない個人情報は持たない、秘密の値は必要なところにだけ渡す、といった備えです。更新が間に合わなかったときの保険になります。

## おわりに

PHP をほとんど触ったことがない身としては、Web の 7 割が PHP で動いていたことがいちばんびっくりでした。

今回の騒ぎは、「みんなが使っている」と「直す前に漏れた」がたまたま重なったせいでした。どの言語を選んでも穴は絶対に今後も出てくるので、すぐ更新できる状態にしておくのがいちばんの備えになりそうです。

PHP のサーバーを抱えている皆さん、健闘を祈ります……！（祈ることしかできません）
