## はじめに

ログイン後の画面しか存在しない Web アプリケーション、たとえば業務用の SaaS のフロントエンドに何を選ぶかという話です。
これまで何度か Next.js で SaaS アプリケーションを作ったことがあるんですが、ユーザー体験に何かびみょ〜な違和感をずっと感じていました。その違和感の正体を追跡します。

この記事では、App Router の Next.js と、クライアントサイドで完結する SPA を比べます。「Next.js は SaaS に向かない」という話は以前からありますが、SEO やレンダリング戦略といった一般論ではなく、**操作したときに何が起きるか**という挙動のレベルで理由を確認します。

前提は Next.js 16 系の App Router です。挙動が変わる部分は都度書きます。

## 認証済みの画面が持つ性質

まず、認識を揃えるために、対象を限定しておきましょう。ここで言う「ログイン後しかないアプリ（便宜上、以降は SaaS と呼びます）」は、次の性質を持つ画面のことです。

| 性質 | 帰結 |
|---|---|
| データが認証済みユーザー固有 | CDN にも ISR にも載らない |
| 検索エンジンに出さない | SEO 由来の要件がゼロ |
| 1 セッションで何十回も画面を移動する | 初回表示より遷移の回数が支配的 |
| 読むだけでなく書く | 変更してから結果が反映されるまでの速さが体感を決める |

この 4 つを前提として、話を進めることにします。

## 動的ルートは遷移のたびにサーバー往復が要る

App Router の `<Link>` は、ビューポートに入った時点でプリフェッチを試みます。ただしプリフェッチの範囲はルートの種類で変わります。Next.js のドキュメントはこう書いています。

> Static routes are prefetched in full by default with a 5-minute client cache TTL. Dynamic routes are only prefetched if they include a loading boundary, and they do not have a default client cache TTL. For dynamic routes, a server roundtrip is required upon navigation, where the shell is streamed to the client.

認証済みユーザーのデータを表示する画面は、定義上すべて動的ルートです。つまり **SaaS の画面はこの後半の条件にしか当たりません**。

`loading.tsx` を置かなかった場合、遷移は次のようになります。

1. ユーザーがリンクをクリックする
2. クライアントがサーバーに RSC ペイロードを要求する
3. **返ってくるまで、画面は前のページのまま**
4. 到着したら新しい画面が描画される

3 の時間は、そのまま「**押したのに何も起きない時間**」になります。ネットワークの往復時間が UI の応答性に直結する、というのが App Router の既定の挙動です。これは推測ではなく、Next.js のドキュメントが「遷移を遅くする要因」として明示的に挙げている項目です。こいつのせいで、動作が妙にもっさりしているように感じるんですね。冒頭に挙げたびみょ〜な違和感は、これが大きそうです。

対処は `loading.tsx` を置くことです。置けば Suspense 境界が入り、クリックした瞬間にスケルトンが出ます。ここまでやれば、体感は SPA に近づきます（あくまで、近づくだけです）。

ただし、これで埋まるのは「反応が返るかどうか」だけです。3 つ残ります。

- **出てくるものが違う**こと。スケルトンは反応であって情報ではありません。クライアントキャッシュを持つ SPA が同じ場面で表示するのは、少し古いかもしれない**実データ**です。読める内容がその場にあり、スクロール位置も目線も切れません。応答の速さは追いついても、情報が届く速さは追いつきません。

- これが**全ルートに対して手作業で保証すべき事項**になること。境界を置き忘れたルートだけ遷移が固まる、という状態が起こりえます。SPA では境界の有無に関わらずクライアント側のルーティングが即座に走るので、置き忘れという事故そのものが発生しません。

- スケルトンが出たあとの中身は依然としてサーバーから来ること。プリフェッチが届くのは静的でキャッシュ可能な部分までなので、**見たい当のユーザー固有データはその対象外**です。次の節がその話です。

仮にスケルトンを出しても、データが表示されるわけではないので、体感のびみょ〜なもっさりは完全には排除しきれません...

## キャッシュできないデータをサーバーで取る意味

そもそも、なぜ RSC はデータ取得をサーバーに寄せるのかという話です。

サーバーでレンダリングする利点は、大まかに 2 つあります。ひとつは、**一度作った結果を使い回せること**。もうひとつは、**クライアントに送る JavaScript を減らせること**です。

前者は、主にSSGやISR、CDN キャッシュなどが該当しますが、認証済みユーザー固有のデータに対しては**成立しません**。ある利用者のダッシュボードのレンダリング結果は、その利用者にしか配れません。どのみち共有先が 1 人なので、共有によって得られる利益は基本的にはゼロです。にもかかわらず、レンダリングをサーバーに置いたことによる往復のコストは発生します。あんまり嬉しくない。

つまり、SSR は「多数で共有できる計算」に対して効く仕組みであって、共有できない相手に使うと**コストだけが残ります**。公開ページで Next.js が強いのと、認証済み画面で持て余すのは、同じ性質の裏表です。

後者の「JavaScript を減らせる」については、次の節で触れます。

## 結局ほとんどが `'use client'` になる

SaaS の画面を構成する要素を並べます。ソートとフィルタのあるテーブル、バリデーション付きのフォーム、モーダル、ドラッグ&ドロップ、リアルタイム更新。

いずれもインタラクティブなので、すべてクライアントコンポーネントになります。

前の節で保留した「JavaScript を減らせる」という利点は、ここで消えます。画面のほぼ全域がクライアントに送られるしかないので、削減できる量が残っていません。

そして、利点が消えてもコストは残ります。`'use client'` の境界をどこに引くか、サーバーコンポーネントから何を props で渡せるか（関数は渡せない、シリアライズ可能な値のみ）、データ取得をどちら側に置くか。この判断が全ファイルに発生します。

**得るものがほぼゼロの分割に対して、設計コストだけを払っている状態**になります。

## TanStack Query を入れれば解決するのか

ここまでの差の多くは、クライアントキャッシュさえ持てば埋まります。ここまで読んで、「じゃあ Next.js のまま TanStack Query を使えばいいんじゃね？」と思っている方もいらっしゃるのではないでしょうか。

確かに、理屈の上では成立します。データ取得をすべてクライアントに寄せ、サーバー側で `cookies()` / `headers()` / `searchParams` を触らなければ、ルートは静的にプリレンダされます。静的ルートは全体がプリフェッチされ、クライアントキャッシュも 5 分保持されるので、遷移は実際に速くなります。

問題は、その条件が実務でほとんど満たされないことです。

```tsx
// app/(app)/layout.tsx
export default async function Layout({ children }) {
  const session = await getSession(); // 内部で cookies() を読む
  return (
    <>
      <Header user={session.user} />
      {children}
    </>
  );
}
```

ヘッダーにログイン中の利用者名を出すだけのレイアウトです。しかしトップレベルで `cookies()` を読んだ時点で、**配下のルートはすべて動的になります**。静的プリレンダの前提が崩れ、遷移時のサーバー往復が戻ってきます。

しかもこの劣化はビルドを通り、エラーも出ません。レイアウトに 1 行足しただけで全ルートの遷移が遅くなる、という形で静かに起こります。タチが悪いですね。

もうひとつ、両方のキャッシュを併用した場合の問題があります。一覧は RSC で取得し、編集パネルだけ TanStack Query で扱う、といった構成です。この 2 つのキャッシュは互いを認識しません。

- `revalidatePath()` は TanStack Query のキャッシュを無効化しない
- `queryClient.invalidateQueries()` は RSC のキャッシュを無効化しない

結果、「更新したのに片方の表示だけ古い」が、再現性の低い不具合として出ます。**どちらに倒すかを決めきり、混在させない**ことが要件になります。

そして全面的に TanStack Query に倒した場合、Next.js が担っているのはルーティングとバンドルと静的シェルの生成であり、RSC も Server Actions も使っていません。Next.js のせっかくの強みが全然活かされません。その割にこれまで挙げたような面倒ごとがひっついて周ります。ならわざわざ採用する理由もないと思います。

それでも採用理由を探すなら、公開ページと同一コードベースにできる、チームがすでに習熟している、といった**体験の外側の事情**になるでしょう。

## 境界線をどこに引くか

以上を踏まえると、判断は「Next.js か SPA か」ではなく、**ページごとにどちらの性質かを見る**という形になります。

| ページの性質 | 向いている構成 | 理由 |
|---|---|---|
| 全員に同じ内容 / 更新が遅い | SSG / SSR | 計算結果を共有できる。SEO と初回表示が効く |
| 認証済み / ユーザー固有 | SPA | 共有できないので、サーバーに寄せる利益がない |

同じプロダクトの中で、ランディングページ・料金・ドキュメントは前者、ログイン後のアプリ本体は後者です。この 2 つを別のアプリケーションとして分け、サブドメインで分割するのが素直な形になります。

## SPA を選ばない場合

例外として挙げられるのは次のようなケースです。

- **ログイン後の画面に、初見の利用者が直接踏む入口がある**。共有リンク、招待リンク、決済フローの入口など。初回表示の速さが成果に直結する
- **初期表示するデータ量が極端に多く**、サーバーで整形して返した方が明確に速い
- **JavaScript の実行環境に制約がある**。低スペック端末が前提、埋め込みブラウザ、規制上の要件など
- **既存資産やチームの習熟がすでに Next.js に寄りすぎている**。分割の設計コストの方が高くつく

最後の項目は技術的な優劣の話ではありませんが、実務では最も頻度が高い理由でしょう。

## SPA を選んだときに払うコスト

公平のために書いておきます。

- **初期バンドルが大きくなる**。ルート単位のコード分割で緩和しますが、最初の 1 回は Next.js より不利です。ログイン後の画面は最初の 1 回より 2 回目以降の頻度が支配的なので許容できる、というのが前提です。

- **認証チェック中の表示が不安定になる**。何も対策しないと、ログイン画面が一瞬見えてからダッシュボードに遷移する、といった挙動になります。認証状態の判定が終わるまで描画を保留する、あるいはサーバーが発行した Cookie を初回描画前に確認する作りで解消できます。構造的な欠点ではなく、実装で詰める箇所です。

## まとめ

判断の根拠を 1 行にすると、こうなります。

> キャッシュできないデータに対して、サーバーへ寄せる利益はない。

SSR が価値を出すのは、**同じレンダリング結果を多数で共有できるとき**です。認証済みユーザー固有の画面はこの条件を満たさないため、往復のコストだけが残ります。そこに、動的ルートの遷移がサーバー応答を待つこと、クライアントキャッシュの既定寿命が 0 であることが重なり、操作のたびの応答性に差が出ます。これがびみょ〜な違和感の正体だと認識しています。

必ずしも Next.js が劣ったわけではなく、**最適化している軸が違う**というだけの話です。公開ページでは同じ性質が利点として働きます。そのかわり、ログイン後の画面では SPA を採用することをお勧めさせていただきます。

これは議論の余地のある領域だと思いますので、皆さんの考えもぜひ教えてください！
