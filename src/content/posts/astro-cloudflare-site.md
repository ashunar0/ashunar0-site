## はじめに

このサイトは Astro で作りました。プロジェクトを作ったのが 2026 年 8 月 6 日、独自ドメインで記事を公開したのが 8 月 8 日です。間に挟まったのは 3 日でした。

Astro を触るのは初めてでしたが、想像していたよりずっと少ない手数で済みました。そして作り終えてみると、良かったのは速さや手軽さよりも、**作り方の向きが自分に合っていたこと**だったな、と思っています。

この記事では、なぜ自分のサイトを作ろうと思ったのか、なぜ Astro を選んだのか、実際に作って何が良かったのかを順に書きます。

## なぜ自分のサイトを作ったのか

出発点は単純で、エンジニアの方のブログを読んで「自分のブログサイトを持っているのかっこいい！」、と思っていたからです。

それまで記事は Zenn と Qiita に書いていました。ただ、どちらも流れてくるのが AI の使い方の話ばかりで、技術そのものの話が少ないと感じるようになりました。自分が書きたい・読みたいものとは少し違う...それなら自分の場所で、自分の好きな話題だけを出していけばいいのではないか、と思い始めました。

もうひとつ理由があります。少し前に自分用の UI ライブラリを作っていて、その過程で「自分はこういうデザインにしたい」というものが固まってきました。作ったからには使う場所が要ります。自分のサイトはその出力先としてちょうどよかったんです。

## なぜ Astro を選んだのか

こういうものを作るとき、まず候補に挙がるのは Next.js だと思います。実際、自分もそのつもりでした。

ただ、過去に 2 度失敗しています。

1 回目は、学習目的で Markdown をレンダリングして表示するタイプのブログを Next.js で作ったときです。動くには動いたのですが、やけにもたつく。原因はきちんと分析しきれていないので断定はしませんが、この規模のものにこんなに苦労するものなのか、という感触だけが残りました。

2 回目は、プログラミングスクールの教材サイトを作ったときです。Next.js を Cloudflare に載せるために OpenNext を使ったのですが、Markdown のレンダリング周りでエラーが出て動かせませんでした（もしかしたらもう解決されてるかもしれませんが）。結局 Vercel にデプロイして落ち着いたものの、もったいないなぁというモヤモヤが残りました。

この 2 回に共通しているのは、**やりたいことは「Markdown を読んで HTML にして配る」だけなのに、そこに至るまでの部品が多すぎる**ということです。Next.js が悪いという話ではなくて、自分がやろうとしていることに対して必要以上に複雑だ、というだけです。もっとシンプルでいいはずでした。

そこで Astro です。決め手は 2 つでした。

- **Markdown をそのまま記事にできる。** ファイルを置けば記事になります。レンダリングのために何かを組む必要がありません
- **Cloudflare にそのまま乗る。** 自分は Cloudflare が好きなので、ここで詰まらないのは大きいです。OpenNext のような変換層を挟まずに済みます

自作の UI ライブラリを使ってみたいという動機もあったので、Astro + Cloudflare でシンプルに作ってみようか、という流れで始めました。

## ファイルを置けば記事になる

まず、期待していたところは期待どおりでした。`src/content/posts/` に Markdown を置けば、それがそのまま記事のページになります。ファイル名が URL になるので、`mac-dev-setup.md` を置けば `/posts/mac-dev-setup/` で開けます。

記事の frontmatter には型を付けられます。

```ts
const posts = defineCollection({
  loader: glob({ pattern: '**/[^_]*.{md,mdx}', base: './src/content/posts' }),
  schema: z.object({
    title: z.string(),
    description: z.string(),
    pubDate: z.coerce.date(),
    updatedDate: z.coerce.date().optional(),
    tags: z.array(z.string()).default([]),
    draft: z.boolean().default(false),
  }),
});
```

これだけで、`title` を書き忘れた記事はビルドで落ちますし、記事を扱うコードの側では `post.data.tags` に補完が効きます。`draft: true` の記事を一覧から外す処理も、この型があるので数行で済みました。

やりたかったのは本当にこれだけだったので、ここで詰まらないというだけで選んだ甲斐がありました。

## 足した機能が、実行時に何も残らない

ただ、実際に良かったと感じたのはその先でした。

サイトを作っていると、だんだん欲しいものが増えていきます。SNS に貼ったときのカード画像が欲しい。記事に URL を貼ったらリンクカードになってほしい。トップに技術ロゴを並べたい。普通ならこのあたりで、ページはじわじわ重くなっていきます。

Astro だと、これらがどれもビルド中に終わってしまいます。

**OG 画像**は、記事ごとに png をビルド時に書き出しています。satori が HTML/CSS を svg にして、resvg がそれを png にする、という流れを `src/pages/og/[...slug].png.ts` に置いてあります。実行時に画像を生成するサービスを用意する必要はなく、Cloudflare には出来上がった png が静的ファイルとして乗るだけです。

**リンクカード**は、remark プラグインを自分で書きました。段落に URL だけが単独で置かれていたら、その URL の OGP を読んでカードの HTML に差し替える、という処理です。

ここが気持ちよかったところなのですが、**OGP を取りに行くのがビルド中なので、CORS もキャッシュも API も要りません**。ブラウザから他所のサイトを fetch しようとすると必ずぶつかる問題が、まるごと存在しなくなります。取得に失敗した URL はカードにせず普通のリンクとして残すようにしてあるので、相手のサイトが落ちていてもビルドは通ります。

**技術ロゴ**は astro-icon で置いています。ビルド時に svg として HTML に埋め込まれるので、アイコンフォントもアイコン用の JS も乗りません。

つまり、機能を 3 つ足したのに、ブラウザに届く JavaScript はほとんど増えていません。目次のハイライトやテーマの切り替えのような、どうしてもブラウザで動く必要があるものだけが数行ずつ残っています。

React も入れてはいますが、置いただけでは静的な HTML になります。動かしたいコンポーネントにだけ指示を書く形なので、「React を使っている」ことと「React をブラウザに送っている」ことが切り離されています。

前に Next.js で作ったブログがもたついた理由を、自分はまだ説明できません。ただ、今回は**重くなりようがない**という感触があります。足したものが実行時に残っていないので、重くなる余地がそもそもない。

## 引き算ではなく、積み上げ

作り終えてみて、気持ちよかったのは速さそのものではなくて、**作り方がボトムアップに積み上げるやり方だったこと**でした。

Next.js は、始めた時点でだいたい全部揃っています。ルーティングも、画像最適化も、キャッシュも、サーバー側で動く仕組みも、最初からそこにあります。だから作業は引き算になります。要らない機能を切り、余計な処理が走らないように気をつけ、送られてしまうものを減らしていく。

Astro は逆でした。何もないところから始まって、要るものだけを足していきます。記事が要るから Markdown を置く。カード画像が要るから生成する処理を書く。React が必要なコンポーネントにだけ React を届ける。**足していないものは、そこに無い。**

この向きの違いは、たぶんフレームワークの優劣の話ではありません。ただ自分は、後者のほうが圧倒的に気持ちよく作れるというだけです。

同じことがバックエンドでもあって、自分は Rails があまり得意ではないのに Hono は好きです。理由はまったく同じで、Hono はゼロから必要なものだけ積み上げていける道具だからです。Rails は最初から全部あって、レールから外れるときに引き算をすることになります。それが自分には合わなかった。

必要最低限しかない状態が、使っていて気持ちいい。今回 Astro を触って一番良かったのは、たぶんそこです。

## 詰まったところ

順調な話ばかり書きましたが、詰まったところもありました。特に効いた 2 つを残しておきます。

### 記事の拡張子は .md にする

Astro は `.md` と `.mdx` のどちらでも記事を書けます。MDX なら中に JSX を書けるので、最初は何となく `.mdx` で置いていました。

これでビルドが落ちます。原因は、Markdown の autolink 記法です。

```md
<https://example.com>
```

URL を山括弧で囲むとリンクになる、という Markdown の書き方なのですが、MDX ではこの `<` が **JSX タグの開始**として解釈されます。`https:` がタグ名として不正なので、そこでパースが止まります。

JSX を書かないなら `.md` にしておけば済む話でした。拡張子を変えても URL は変わりません。逆に、JSX を埋めたくなった記事だけ `.mdx` にすればいいと思います。

なお、記事のファイルを消したり拡張子を変えたりしたときは、キャッシュを消さないと古いパスを掴んだままエラーになることがあります。

```bash
rm -rf .astro dist node_modules/.astro
```

### スマホだけスクロール位置がおかしい

こちらは Astro の話ではないのですが、原因にたどり着くまでが長かったので書いておきます。

記事ページをスマホで開くと、なぜか**本文の途中から始まる**という不具合が出ました。厄介だったのは、開発サーバーでも、Chrome の幅を 390px にしても、まったく再現しなかったことです。

再現したのは、**本番ビルドを WebKit で開いたとき**でした。iOS は Chrome も中身が WebKit なので、ここを踏むと全部の iPhone で起きます。

原因は、WebKit が **inline module script をスタイルシートの適用前に実行する**ことでした。目次には現在位置をハイライトする処理があり、その中で該当箇所へスクロールさせています。目次は狭い画面では CSS で消してあるので、スマホでは動かない前提のコードでした。ところが WebKit では、スクリプトが走る一瞬だけその CSS が効いておらず、目次が本文の下に並んでいる状態でスクロールが発生していました。

学びとしては 2 つです。

- **スマホだけ挙動が違うと言われたら、Chrome の幅を変えるだけで済ませない。** 本番ビルドを WebKit で開いて確認する
- **CSS が当たっている前提の DOM 操作は、初回実行時には成り立たないことがある。** 「`display: none` だから安全」は WebKit では保証されない

## おわりに

初めて Astro を触りましたが、やりたかったことに対してちょうどいい道具でした。

ただ、この記事で一番言いたかったのは Astro が良いという話ではありません。**道具には、全部ある状態から引いていくものと、何もない状態から積んでいくものがある**ということです。そしてどちらが合うかは、たぶん人によって違います。

自分は後者でした。Next.js でうまくいかなかったのも、Rails が得意にならなかったのも、今にして思えば同じ理由だったのだと思います。逆に Hono や Astro は、初めて触ったのに迷いませんでした。

もし前に何かのフレームワークで「なんだかしっくりこない」と感じたことがあるなら、それは実力の話ではなくて、向きが逆だっただけかもしれません。一度、積み上げるタイプの道具を触ってみると発見があると思います。

これからは自分の場所で、好きなことを書いていきます。
