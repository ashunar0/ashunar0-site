## はじめに

現在、内定者インターンで触っているシステムが、スタイルをSCSSで書いていました。僕は普段Tailwindしか使っていなくて、そもそもSCSSに触れる機会というものがこれまでほとんどありませんでした。名前はもちろん知ってるんだけど、CSSと何が違うの...？という感じだったので、今回はそれを調べてみました。

## SCSSはブラウザが読めない

いちばん大事な前提として、**ブラウザは`.scss`ファイルを読めません。**

`.scss`は、ビルドの段階で`.css`に変換してから配ります。変換した後のファイルにはSCSSの構文はひとつも残っていません。この「CSSを吐くための言語」のことをCSSプリプロセッサと呼びます。なんだかTypeScriptがJavaScriptにコンパイルされるのに似ていますね。

つまりSCSSは、CSSを置き換えるものではありません。CSSを**書くための**言語です。

## 何のために作られたのか

Sassが最初に登場したのは2006年、Hampton Catlinによるものです。当時のCSSには変数がありませんでした。ブランドカラーを1色変えたければ、その色を書いた箇所を全部探して書き換えるしかありません。同じ`border-radius: 4px; box-shadow: ...`の3行を、ボタンにもカードにもモーダルにもコピペする、という書き方が普通でした。

CSSは元々、文書に見た目を与えるための宣言的な記法として設計されたもので、大規模なアプリのスタイルを何万行も管理する道具としては作られていません。そこに変数・再利用・分割といった、プログラミング言語なら当たり前にあるものを持ち込もう、というのがSassの出発点です。

## SassとSCSSは何が違うのか

ここで名前がややこしいのですが、SassとSCSSは別物ではありません。**Sassという言語に、記法が2種類ある**というだけです。

最初にできたのはインデント記法（`.sass`）でした。Haml由来で、波かっこもセミコロンも書きません。今で言うとPythonやRubyっぽいですね。

```sass
// .sass（インデント記法）
.card
  color: red
  .title
    font-weight: bold
```

見ての通り、CSSとは見た目がまったく違います。既存のCSSをそのまま貼り付けても動かないので、導入のハードルが高いという問題がありました。

そこで2010年のSass 3.0で、CSSそっくりの記法が追加されました。これがSCSS（Sassy CSS）で、拡張子は`.scss`です。

```scss
// .scss
.card {
  color: red;
  .title {
    font-weight: bold;
  }
}
```

SCSSはいわばCSSの**スーパーセット**です。有効なCSSはそのまま有効なSCSSとして通ります。つまり既存の`style.css`を`style.scss`にリネームするだけで動くので、少しずつSassの機能を足していけます。今現場で見かけるのもこれなので、この記事でもSCSS記法で扱うこととします。

なお処理系は移り変わっていて、オリジナルのRuby Sassは2019年、node-sassは2024年にEOLを迎えています。今の実装はDart Sassです。こういった変遷も相まって、古い記事のコマンドがそのまま動かないこともちらほらあるらしいです。厄介ですね。

## SCSSが持ち込んだもの

では具体的に何が書けるようになったのかを並べてみます。ここでは深入りせず、雰囲気だけ掴んでください。

### ネスト

親子関係を入れ子で書けます。セレクタを毎回フルで書き直さなくて済みます。

```scss
.card {
  padding: 16px;
  .title { font-weight: bold; }
  &:hover { background: #eee; }
}
```

### 変数

値に名前を付けて使い回せます。

```scss
$primary: #3b82f6;
$radius: 4px;

.button { background: $primary; border-radius: $radius; }
```

### ミックスイン

スタイルの塊に名前を付けて、引数付きで呼び出せます。関数のような感覚で使えるのが変数との違いです。

```scss
@mixin button($bg) {
  padding: 8px 16px;
  border-radius: 4px;
  background: $bg;
}

.primary-button { @include button(#3b82f6); }
.danger-button  { @include button(#ef4444); }
```

### 継承

別のセレクタのスタイルをまるごと引き継ぎます。

```scss
.button { padding: 8px 16px; border-radius: 4px; }
.danger-button { @extend .button; background: #ef4444; }
```

### ファイル分割

ファイルを分けて読み込めます。`_`で始まるファイル（パーシャル）は単体ではCSSを出力せず、読み込まれる部品として扱われます。

```scss
// _variables.scss と _button.scss を読み込む
@use 'variables';
@use 'button';
```

### 演算と組み込み関数

四則演算ができ、色を明るくする・暗くするといった計算も書けます。

```scss
@use 'sass:color';

.card { width: 100% / 3; }
.button:hover { background: color.adjust(#3b82f6, $lightness: -10%); }
```

### 制御構文

条件分岐とループがあります。同じ形のクラスを量産するときに使います。

```scss
@each $name, $color in (primary: #3b82f6, danger: #ef4444) {
  .text-#{$name} { color: $color; }
}
```

出てくるのは`.text-primary`と`.text-danger`の2つのクラスです。`#{}`は変数を文字列に埋め込む書き方で、これを使うとクラス名そのものを組み立てられます。

並べてみると、変数・関数・ループ・モジュール分割と、プログラミング言語なら当たり前にあるものが一通り揃っています。そして重要なのは、**これらは全部ビルド時に展開されて消える**ということです。ブラウザに届く頃には、ただのCSSに戻っています。

## 後からCSSに取り込まれたもの

SCSSが登場したのは2006年です。それから20年近く経って、CSS自身もかなり進化しました。上に並べた機能のうち、いくつかはもうCSSだけで書けます。

### ネスト

2023年に主要ブラウザが出揃い、ネストはCSSの標準機能になりました。書き方もSCSSとほぼ同じです。

```css
/* ただのCSS */
.card {
  padding: 16px;
  .title { font-weight: bold; }
  &:hover { background: #eee; }
}
```

ただし、ひとつだけSCSSと決定的に違うところがあります。**`&`に文字列をくっつけられません。**

```scss
/* SCSS では書ける */
.card {
  &__title { font-weight: bold; }  /* → .card__title */
}
```

SCSSの`&`は親セレクタの文字列に置き換わるので、`&__title`は`.card__title`という別のクラス名になります。BEMを書くときの定番です。

一方、CSSの`&`は文字列ではなくセレクタそのものを指します。`&__title`と書くと「`__title`という名前の要素かつ`&`」という意味になってしまい、どの要素にも当たりません。エラーにもならず、ただ効かないスタイルができあがります。

レガシーなSCSSを読むと`&__`だらけなことが多いのですが、これはSCSSを外すと真っ先に壊れる部分です。

### 変数

CSSにもカスタムプロパティ（CSS変数）があります。

```css
:root { --primary: #3b82f6; }
.button { background: var(--primary); }
```

見た目が似ているので同じものに見えますが、**`$primary`と`--primary`は別物です**。SCSSの変数はビルド時に値へ置き換わって消えるのに対し、カスタムプロパティはそのままブラウザに届いて、実行時に評価されます。

| | SCSSの`$変数` | CSSの`--変数` |
| --- | --- | --- |
| 生きている場所 | ビルド時 | ブラウザ |
| ビルド後 | 消える | 残る |
| あとから値を変える | できない | できる（JSからでも） |
| 開発者ツールで見える | 見えない | 見える |
| メディアクエリの条件に使う | できる | できない |
| クラス名やプロパティ名を組み立てる | できる | できない |

下2行が効いてくる場面があります。ブレークポイントは`@media (min-width: $bp)`とは書けますが、`@media (min-width: var(--bp))`とは書けません。カスタムプロパティはあくまでプロパティの「値」の場所にしか置けないからです。

逆に、ダークモードのようにあとから色を差し替えたい場合、SCSSの変数では実現できません。ビルドした時点で色が確定してしまっているので、切り替える先が残っていないからです。

つまりどちらかが上位互換ということはなく、棲み分けがあります。テーマや動的な値はカスタムプロパティ、ビルド時に決まる定数はSCSSの変数、という使い分けになります。

### 演算

四則演算は`calc()`でできます。SCSS側は`/`が割り算ではなくなった（`math.div()`を使う）という変更もあったので、今は素直に`calc()`で書くほうが分かりやすい場面が多いです。

```css
.card { width: calc(100% / 3); }
.title { font-size: clamp(16px, 4vw, 32px); }
```

`clamp()`や`min()`/`max()`のように、CSS側にしかない計算もあります。これらは画面幅に応じて実行時に計算されるので、ビルド時に値が決まるSCSSでは代わりが書けません。

### 色の操作

色を混ぜたり明るさを変えたりする計算も、CSSでできるようになりました。

```css
.button:hover { background: color-mix(in srgb, var(--primary) 90%, black); }
```

`color-mix()`は2023年から主要ブラウザで使えます。SCSSの`color.adjust()`と違って、カスタムプロパティを渡せるのが大きい点です。ビルド時に色が分かっていなくても計算できます。

こうして並べると、SCSSの代表的な機能はかなりCSS側に来ています。ただし置き換えではありません。ネストは`&`の扱いが違い、変数は動くタイミングが違います。「SCSSを外してCSSにする」という作業は、決して機械的な置換では済まないようです。

## SCSSにしかないもの

とはいえ、CSSもかなり進化していて、いまSCSSを使う意味ってあるの？という疑問が浮かびます。まだSCSSにしか無いものはなんなのでしょうか？実際並べてみると、それはどれも「ビルド時に展開して消える」からこそできる芸当でした。

### ミックスイン

引数を取れるスタイルの塊は、CSSには相当するものがありません。

```scss
@mixin flex-center($gap: 0) {
  display: flex;
  align-items: center;
  justify-content: center;
  gap: $gap;
}

.header { @include flex-center(8px); }
```

CSSのカスタムプロパティで代用できるのは「値」だけです。`display`と`align-items`と`justify-content`をまとめて1行で呼び出す、という書き方はできません。CSSにはルールを別のルールへ展開する仕組みが無いからです。

これはSCSSの機能の中でも、いまだに置き換えの効かない代表格です。

### ループでクラスを量産する

`@each`と`#{}`を組み合わせると、クラス名そのものを生成できます。

```scss
$spacings: (0, 4, 8, 16, 32);

@each $s in $spacings {
  .mt-#{$s} { margin-top: #{$s}px; }
}
```

これで`.mt-0`から`.mt-32`までが一気に出力されます。CSSでは、セレクタの名前を計算で組み立てることはできません。カスタムプロパティは値の場所にしか置けないので、`--name`をクラス名に埋め込むこともできません。

ちなみにこれは、Tailwindが`mt-4`のようなクラスをあらかじめ用意しているのと発想としては近いものです。ユーティリティクラスをまとめて作る、という需要はSCSSの時代からあったようですね。

### モジュール分割

`@use`でファイルを分けられます。ファイル名の先頭に`_`を付けたもの（パーシャル）は単体ではCSSを出力せず、部品としてだけ扱われます。

```scss
// _colors.scss
$primary: #3b82f6;

// main.scss
@use 'colors';
.button { background: colors.$primary; }
```

読み込むと`colors.`という名前空間が付くので、どのファイル由来の変数なのかが呼び出し側に残ります。また、名前が`-`や`_`で始まるメンバーはそのファイルの外から参照できません。

CSSにも`@import`はありますが、あれは実行時に別ファイルを取りに行く仕組みです。読み込みが直列になるので性能上は避けられがちで、そもそも「変数を共有する」用途には使えません。SCSSの`@use`はビルド時にファイルを1つに結合するので、届くCSSは1ファイルのままです。

なお、SCSSの`@import`はすでに非推奨です。Dart Sass 1.80.0で廃止予定が告知されていて、3.0.0で削除されます。古いコードで見かけたら、`@use`に置き換わっていく途中のものだと考えるのが妥当でしょう。

### 条件分岐

`@if`が書けます。ミックスインの中で、引数によって出力するスタイルを変えたいときに使います。

```scss
@mixin button($variant) {
  @if $variant == 'outline' {
    border: 1px solid currentColor;
    background: transparent;
  } @else {
    border: none;
    background: #3b82f6;
  }
}
```

出力されるCSSに`@if`は残りません。どちらか片方の中身だけが書き出されます。

### 継承（ただし今はあまり使われません）

`@extend`は、別のセレクタのスタイルをまるごと引き継ぐ機能です。

```scss
.button { padding: 8px 16px; }
.danger-button { @extend .button; background: #ef4444; }
```

一見ミックスインより便利に見えますが、実際に出力されるのは`.button, .danger-button { padding: 8px 16px; }`のように、元のルールへセレクタを追加する形です。継承元があちこちで使われていると、出力されるセレクタが芋づる式に膨らみます。メディアクエリをまたいで`@extend`することもできません。

そのため今は、ミックスインで書くほうが安全とされています。レガシーなコードで見かけることはありますが、新しく書く理由はほぼ無いといえるでしょう。

## まとめ

調べてみると、SCSSとCSSの関係はかなりはっきりしていました。

SCSSはビルド時に展開されて消える言語です。だからSCSSができるのは、あくまで**書くときの手間を減らすこと**に限られます。逆に、実行時に効いてほしいもの、つまりテーマの切り替えや画面幅に応じた計算は、そもそもSCSSの守備範囲ではありません。そしてその領域は、カスタムプロパティや`clamp()`としてCSS側に揃いました。

一方でSCSSに残ったのは、ミックスイン・ループ・モジュール分割といった、まさに「書くときにしか要らないもの」です。CSSは配られて実行されるものなので、この層は今後もCSSには入らないんじゃないかと思います。

いま新規で書くならTailwindなり別の選択肢があるとは思いますが、SCSSが解こうとしていた問題自体は今も無くなっていません。ただ単にレガシーなものだと思っていましたが、意外と地続きでした。
