## はじめに

最近、「エディタを開かなくなったから、AI が賢くなったから、TypeScript はもうオワコン」という趣旨の投稿をちらほら見かけます。

マジ？？

AI にコードを書かせるようになって、確かにエディタを開く時間は激減しました。カーソルを合わせて補完を見て手で型を書く...なんてことはもうほとんど、というか全くありません。でも、それで型まで要らなくなるとは到底思えません。むしろ AI に書かせるからこそ、型の出番は増えていると思っています。

人間も AI も、どこかで必ず見落とします。しかも AI は、人間が一行ずつ読みきれない速さでコードを書きます。だから、間違いを見つける仕組みを何重にも何重にも重ねて、AI の出力に再現性を持たせる必要があります。型は、その中でもいちばんと言っていいほど大事な部品です。

この記事では、要らないと言われる理由もちゃんと踏まえたうえで、それでも TypeScript が要る理由について考察していきます。

## 確かに要らなくなったもの

AI の台頭によって、型の役割が少し変わったことは、認めざるを得ません。先に、要らなくなったものを認めておきます。

まず、補完です。`post.` と打てばプロパティの一覧が出てくるし、関数にカーソルを合わせれば引数の型が出てきます。これらは人間がエディタで書くときには欠かせませんでしたが、コードを書くのが AI になってからは、見ることがまったくなくなりました。Hono RPC も、補完が出るまでの速さを気にして書き方を工夫していた時期もありましたが、AI に書かせるならそこはもうほとんど関係ありません。

型を手で書く手間もなくなりました。JS に型を一つずつ付けていく作業も、ジェネリクスを組み合わせる型パズルも、今は AI がやってくれます。

ここまでは、TypeScript は要らないという意見にも同意です。人間がエディタで書くのを助けるための型は、確かに出番が減りました。

でも、型の役目はそれだけではありません。書かれたコードが型のとおりになっているかを tsc が確かめて、合わなければエラーとして止めてくれます。こちらは、今も変わらずに残っています。この記事で要ると言っているのは、こっちの型です。

## 人間も AI も、必ず間違える

AI は本当に賢くなりました。ちょっとした機能なら、説明するだけで一発で動くものが出てきます。型がなくても、たいていはちゃんと動くコードを書いてくれます。人間よりもはるかに高いコーディング能力を有していることは疑う余地もありません。

でも、あくまで「たいてい」です。

どんなに頭が良くても、見落としは必ずあります。人間だってそうです。ベテランが書いて、レビューを何人も通しても、バグは出ます。AI でもそれは同じで、賢くなって見落とす回数は減っても、ゼロにはなりません。

だから開発で大事なのは、間違えない人や AI を探すことではなく、間違えたときに気付ける仕組みをどれだけ持っておけるかです。型、テスト、lint、レビューなど、どれも一つだけでは漏れがあるので、何重にも重ねて、すり抜ける見落としを一つでも多く減らしていきます。不確実な要素をどこまで減らせるか、という勝負です。

AI が賢くなっても、この考え方は変わりません。しかも AI は、人間とは比べものにならない量のコードを書きます。1 行あたりの見落としがどれだけ少なくても、全体で見れば、どこかに必ず残ります。

そして、その残った見落としを人間が全部拾うのは、もう無理です。AI が数分で書いた何百行ものコードを、毎回一行一行読んで確かめていたら、AI に書かせている意味がありません。人間の目で拾いきれない分は、機械に確かめてもらうしかないんです。

もちろん、個人開発で自分しか使わないものなら、好きにやればいいと思います。壊れても困るのは自分だけです。でも、仕事で作るものや、誰かが使うソフトウェアを作るなら、見落としを減らす仕組みを自分から手放す理由はないと思っています。

## 型とテストは、見ているものが違う

機械に確かめてもらうなら、テストがあります。振る舞いはテストで、外から入ってくる値は Zod で、書き方は lint で守ればいいから、型までは要らない、という意見もよく見かけます。

型の正しさは誰も保証しない、という指摘もあります。AI が型もコードも書くと、型そのものが間違っていても tsc は通してしまいます。たとえば、NULL になりうるカラムを `string` と書いても、エラーにはなりません。

これはそのとおりです。ただ、それを言うならテストも同じです。テストが正しいかどうかも、誰も保証してくれません。AI が書いたテストに AI が書いたコードを通して、全部通ったとしても、テストのほうが間違っていることはあります。

しかも、テストが確かめられるのは、書いた場面だけです。型は、型で書ける範囲なら、すべての場合を確かめます。

たとえば、記事の公開日時を文字列にする関数です。下書きの記事は、まだ公開日時を持っていません。

```ts
type Post = { title: string; publishedAt: Date | null };

function formatPublishedAt(post: Post) {
  return post.publishedAt.toISOString();
}
```

公開済みの記事を渡すテストを書けば、このテストは通ります。下書きを渡す場面を誰も思いつかなければ、テストは下書きのことを何も言ってくれません。でも型なら、誰も思いつかなくても止まります。

```
error TS18047: 'post.publishedAt' is possibly 'null'.
```

どちらも完璧ではありません。でも見ているものが違うので、重ねておけば、片方をすり抜けたものをもう片方が拾えます。そもそも完璧を求めていないので、「型が正しい保証はない」は、型を捨てる理由にはならないと思っています。

### 型は手で書かない

とはいえ、NULL のカラムを `string` と書けてしまうのは困ります。これは、型を手で書くのをやめれば防げます。

```ts
// db/schema.ts
export const posts = sqliteTable("posts", {
  id: text("id").primaryKey(),
  title: text("title").notNull(),
  publishedAt: integer("published_at", { mode: "timestamp" }), // 下書きのあいだは NULL
});

export type Post = typeof posts.$inferSelect;
// { id: string; title: string; publishedAt: Date | null }
```

Drizzle なら、テーブルの定義から型を作れます。NULL になりうるカラムには、勝手に `| null` が付きます。AI が型を書く場面そのものがないので、型が嘘をつく余地もありません。外から入ってくる値も同じで、Zod のスキーマから `z.infer` で型を作れば、確かめる中身と型が一か所にまとまります。

### tsc は速いし、タダ

型を確かめる時間もトークンも、今はほとんど気になりません。tsc は 7.0 で Go に書き直されて、6.0 の 10 倍くらい速くなりました。最近は Rust に移植した tsrs も出てきて、さらに速くなりそうです。

https://ashunar0.dev/posts/tsrs-rust-port/

トークンもほとんど使いません。tsc は、型が合っていれば何も出力しないからです。AI が読むのは、間違えたときのエラーの数行だけです。

しかもそのエラーには、どのファイルの何行目で、何と何が合わないかが書いてあります。AI はそれを読んで、自分で直せます。tsc で一瞬でわかることを、わざわざ AI にコードを読ませて確かめさせるほうが、よほど時間もトークンもかかりますし、見落としも出ます。

## 毎回同じ形で書かせる

AI のコードを一行一行は読めない、という話をしました。じゃあ人間はどこを見ればいいのかというと、型や lint では確かめられないところだけです。

そのためには、AI に毎回同じ形で書かせることが大事です。書き方が毎回ばらばらだと、どこが決まりどおりでどこが違うのかを、結局全部読んで確かめることになります。毎回同じ形なら、「ここはいつもと同じだから見なくていい、見るのはここだけ」と言えます。AI の出力に再現性を持たせる、というのはこういうことです。

書き方をそろえる道具は、lint、ディレクトリの決まり、CLAUDE.md のような規約など、いろいろあります。型もその一つで、しかもかなり強い道具です。

たとえば、Hono で API を作るときのエラー処理です。前に、失敗を `Result` で返すルールを決めました。

https://ashunar0.dev/posts/hono-error-handling/

```ts
export const publishPost = (
  id: string,
): Result<Post, "POST_NOT_FOUND" | "ALREADY_PUBLISHED"> => {
  const post = posts.find((p) => p.id === id);
  if (!post) return err("POST_NOT_FOUND");
  if (post.status === "published") return err("ALREADY_PUBLISHED");
  post.status = "published";
  return ok(post);
};
```

戻り値の型を `Result` にしておくと、AI はこの形でしか失敗を返せません。`{ message: "..." }` のような別の形で返そうとすると、型が合わずに止まります。`throw` のように型では止められないものは、lint で止めます。こうして、書き方がぶれなくなります。

万が一間違えても気付けます。失敗を一つ足して、handler で扱うのを忘れると、型エラーになります。

```
error TS2339: Property 'value' does not exist on type
'Result<Post, "ALREADY_PUBLISHED" | "POST_NOT_FOUND" | "TITLE_REQUIRED">'.
```

ここまで決まっていると、人間がレビューで見るのは、「公開済みの記事をもう一度公開しようとしたら 409 でいいか」のような、業務の判断だけになります。失敗を返す形が合っているか、全部の失敗を扱っているかは、もう tsc が確かめてくれています。

これが、型でレビューの範囲が狭くなる、ということです。見落とさないように全部を見るのではなく、機械が見られないところだけを人間が見ます。AI がどれだけ速く書いても、人間が追いつけるのはこのやり方だけだと思っています。

最近作っている Hono Kit も、この考え方で作っています。書き方の決まりを型と lint にしてあるので、外れた書き方をするとすぐ止まって、AI に書かせても AI が自分で直せます。

https://ashunar0.dev/posts/hono-kit/

## おわりに

AI に書かせるようになって要らなくなったのは、人間がエディタで書くのを助けるための型です。書かれたものを機械が確かめる型は、今も、むしろ前よりも要ります。

人間も AI も、どこかで必ず間違えます。だから確かめる仕組みを何重にも重ねて、毎回同じ形で書かせて、人間が見る場所を絞ります。型は、そのどちらでも真ん中にいる部品です。

エディタを開かなくなったのは、AI に任せられるようになったからです。でも、任せたものが合っているかを確かめる仕組みまで手放してしまったら、バグだらけのものができあがっても誰も気付けません。せっかく AI が速く書いてくれるなら、その速さのまま安心して出せるように、型はちゃんと使っていきたいと思っています。
