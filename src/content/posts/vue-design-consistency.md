## はじめに

この度、インターンで機会があって、Vue の公式ドキュメントを一通り読みました。細かいところまでとても丁寧に書かれていて、手厚さに驚きました。自分は普段 React ばかり書いているので、どうしても比較しながら読むことになります。そこで今回は、公式ドキュメントから見えた React と Vue の設計思想の違いについて、興味深かったことをまとめてみようと思います。

まず読み終えてとても印象に残ったのは、機能ごとの優劣ではなく、**三つの要素が一つの前提から派生している**ということでした。テンプレート構文という制約、リアクティビティの実装方式、そして仮想 DOM を外す Vapor Mode。この三つは別々の機能に見えて、実は順番に繋がっています。その流れを追ってみましょう。

## テンプレート構文：自由を捨てて何を得たか

Vue のコードを開いて最初に目に入る違いが、テンプレート構文です。

```vue
<template>
  <ul v-if="items.length > 0">
    <li v-for="item in items" :key="item.id">{{ item.name }}</li>
  </ul>
</template>
```

`v-if` も `v-for` も Vue の独自構文です。JSX に慣れていると、ここは素直に違和感がありました。なぜ js で書けるのに独自構文を作るんだろうと。JSX は JavaScript の式なので、新しい構文を覚える必要がありません。UI を返す関数、という説明が最後まで崩れないのは綺麗な設計だと思います。

ただ、その自由には別の側面があります。同じ条件付きレンダリングを JSX で書くとき、書き方が一つに定まりません。

```tsx
// どれも正解
{isLoading && <Spinner />}
{isLoading ? <Spinner /> : null}
if (isLoading) return <Spinner />; // 関数の先頭で早期リターン
```

どれでもちゃんと動きます。ここだけでも 3 つの書き方がありますね。じゃあ同じものを Vue で書いたら？

```vue
<Spinner v-if="isLoading" />
```

基本的にはこれだけです。

### 構造が固定されていると、ビルド時に読める

書き方が一つに定まるということは、コンパイラが構造を読めるということです。Vue のコンパイラはテンプレートを解析して、**どこが静的でどこが動的か**をビルド時に判別します。

```html
<div>
  <div>foo</div>
  <div>bar</div>
  <div>{{ dynamic }}</div>
</div>
```

上の二つは静的なので、初回レンダリングで作った vnode をキャッシュして使い回します。差分の計算自体をしません。

動的な箇所についても、コンパイラは**何が変わりうるか**まで知っています。

```js
createElementVNode("div", {
  class: _normalizeClass({ active: _ctx.active })
}, null, 2 /* CLASS */)
```

最後の `2` はパッチフラグと呼ばれるもので、「この要素は class だけ変わる」という意味です。ランタイムはビット演算でこれを見て、class だけ確認します。全属性を突き合わせる必要がありません。

さらに、動的なノードだけを平坦な配列にまとめます。再レンダリング時にツリー全体をたどらず、その配列だけ見れば済みます。

これらは、テンプレートが解析可能だから成立しています。JSX でこれをやるのは困難です。JSX は JavaScript なので、実行してみるまで何が返るか分かりません。Vue の公式ドキュメントは、テンプレートについて「構文がより決定的であるため静的解析しやすい」と書いています。

Vue のコンパイラはビルド時とランタイムの両方を握っていて、生成コードにヒントを残し、ランタイムがそのヒントで近道をします。片方だけでは成立しない仕組みです。

> 余談ですが、個人的な見解として、書き方が収束するのは AI にコードを書かせる時代だからこそ嬉しい性質かもしれません。JSX だと毎回出力が揺れる or それを抑えるために指示やルールが必要ですが、`v-if` にはその分岐がありません。読む側の認知負荷という意味でも、選択肢が少ないことは効いてきそうです。

## リアクティビティ：再実行するか、追跡するか

そして最も本質的な違いが、状態が変わったときの扱い方です。

React の場合、状態が更新されるとコンポーネント関数が丸ごと再実行されます。その結果を前回の仮想 DOM と比較し、差分だけを実 DOM に反映します。

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  // setCount が呼ばれると、この関数全体が再び実行される
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

つまり React は、何が変わったかを知らないまま、変わったかもしれない範囲を再実行して差分を取るという戦略です。これは非常に素直なモデルで、「UI は状態の関数である」という考え方をそのまま実装したものと言えます。

代償として、不要な再実行を抑えるのは開発者の仕事になります。useMemo や useCallback、依存配列の管理といった作業が必要になるのはこのためです。

対して Vue は、何が変わったかを追跡します。

```vue
<script setup>
import { ref } from 'vue';
const count = ref(0);
// count が変わったとき、count を使っている箇所だけが更新される
</script>
```

ref で作った値は、読み取られた時点で「誰がこの値に依存しているか」を記録します。値が更新されると、記録された依存先だけが再実行されます。コンポーネント関数全体が再実行されることはありません。

この違いは実際の書き味に直結します。Vue では依存配列を書く場面がなく、メモ化を意識する機会も大幅に減ります。「開発体験が良い」と言われる要因の一つは、おそらくここです。

まとめると、こうなります。

|            | React                      | Vue              |
| ---------- | -------------------------- | ---------------- |
| 状態更新時 | コンポーネントを再実行     | 依存箇所のみ更新 |
| 差分の特定 | 仮想 DOM の比較            | 依存関係の追跡   |
| 最適化     | 開発者が明示（メモ化など） | 仕組みが担う     |

### 業界のほうが、Vue に寄ってきた

この二つは真逆で、どちらが良いのかは長いあいだ議論されてきました。その結論が、ここ数年で出つつあります。Solid、Svelte 5 の Runes、Angular の signals、Preact Signals。どれも読み取りを追跡して、依存する箇所だけ更新します。つまり、Vue 側です。

React は依然として、再実行して差分を取るモデルを維持して、最適化は開発者に委ね続けました。そこに React Compiler が出ます。公式はその理由をこう書いています（訳は筆者）。

> この手動のメモ化は面倒で、間違えやすく、保守すべきコードを増やします。

モデルは変えないまま、その上に自動化の層を乗せた形です。とはいえ、長く開発者の仕事としてきた作業を面倒で間違えやすいと認めて、フレームワーク側で引き受けにいったことに変わりはありません。

こうして並べると、**Vue が最初に選んで、そのまま変えなかった方式に、業界のほうが寄っていった**ように見えます。当時は数ある選択肢の一つだったはずのものが、後から効いてきた、ということだと思います。

## Vapor Mode：土台が揃っていたから外せる

三つ目が Vapor Mode です。仮想 DOM を使わず、テンプレートを直接 DOM 操作へコンパイルします。有効にするのは `<script setup vapor>` の一語です。`<script vapor>` や `<template vapor>` でも同じです。

なぜ外せるのか。ここまでの二つがそのまま効いています。

テンプレートは解析可能なので、**どこを更新するか**はビルド時に分かります。リアクティビティは追跡型なので、**いつ更新するか**はランタイムが知っています。両方分かっているなら、そもそも前回の結果と突き合わせて差分を探す工程は要りません。仮想 DOM は、どこが変わったか分からないときに必要になるものです。

### 仮想 DOM を外すと？

まず、更新のコストが下がります。差分を探すという工程がまるごと消えるからです。従来の Vue も、パッチフラグやツリー平坦化で「動的なノードだけを辿る」ところまで削っていました。Vapor Mode はそもそも辿りません。どの DOM をどう操作するかが、コンパイル時に確定しています。

次に、メモリが減ります。仮想 DOM は UI ツリーの複製をメモリ上に持つ仕組みで、レンダリングのたびに VNode オブジェクトの割り当てが発生します。Vapor Mode はこれを作りません。

そしてバンドルが小さくなります。`createVaporApp()` で作った Vapor だけのアプリは、仮想 DOM のランタイムコードを一切含みません。公式には、これによってベースラインのバンドルサイズを大幅に削減できると書いてあります。

結果がどうなったか。3.6.0-rc.1 のリリースノートによると、Vapor Mode は第三者のベンチマーク（js-framework-benchmark）で **Solid と Svelte 5 と同水準の性能を示した**そうです。この二つは signals ベースで速さの代表格だったフレームワークです。Vue はそこに並びました。

React で同じことをすると、構造的に重くなります。JSX は関数なので実行するまで何が返るか決定されず、再実行が前提なので更新箇所も分かりません。仮想 DOM は React にとって最適化ではなく前提の側にあります。外すには両方を変えることになり、既存のアプリを壊さずにやるのは現実的ではないはずです。

面白いのは、Vapor Mode が新しい発明を持ち込んだわけではないということです。テンプレート構文は最初からありました。追跡型のリアクティビティも最初からありました。その二つが揃っていたから、仮想 DOM を外すという選択肢が後から取れた。**外せる位置に立てていること自体が、最初の選択の結果**です。Vapor Mode は、これまでの Vue の設計や選択の必然的な帰結と言えるでしょう。

## 一貫していることが、後から効いてくる

三つを並べ直すと、こうなります。

テンプレート構文は自由度を捨てて、構造をコンパイラに読ませました。リアクティビティは依存を追跡して、更新範囲をフレームワークの側に持たせました。この二つによって「どこを」「いつ」更新するかが揃い、Vapor Mode で仮想 DOM を外せるようになりました。

別々に足された機能には見えません。最初に置いた前提から、順番に派生しています。テンプレート構文を選んだ時点で Vapor Mode が見えていたはずはありませんが、選択が互いに整合していたので、後からその道が現れた、という順序だと思います。

React も一貫はしています。UI を状態から計算する関数として書く、という説明はどこまで行っても崩れません。ただ、その一貫性が向かった先が違いました。再実行を前提に置いたので、最適化は外から足すことになり、React Compiler という層が乗りました。

設計判断の正しさは、選んだ時点では分かりません。分かるのは、その判断が他の判断と噛み合っているかどうかだけです。Vue のドキュメントを読んで面白かったのは、性能の数字よりも、そこが揃っていたことでした。
